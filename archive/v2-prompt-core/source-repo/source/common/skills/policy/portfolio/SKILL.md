# 포트폴리오

검증을 거쳐 완료된 모든 변경 작업은 `.codex/logs/sessions/{YYYY-MM-DD-task-slug}/portfolio-log.md`를 작성한다. 애플리케이션 기능·버그 수정·리팩터링·문서·설정뿐 아니라 `.agents/`, `.codex/`, `.claude/`, `.harness/`의 AI 하네스·스킬·훅·워크플로 변경도 같은 구조로 기록한다. 다른 필수 산출물을 포트폴리오 서술로 대체하지 않는다.

## 근거 수집

현재 작업에서 직접 확인한 근거만 추합한다.

- **사용자 대화**: 사용자가 제시한 도메인·서비스 문제, 수정 요구, 기획 변경 이유, 사용자 제안, 에이전트 제안에 대한 선택과 후속 피드백.
- **실행 근거**: 테스트·lint·build·런타임 사용에서 발생한 오류와 수정 후 결과.
- **설계 근거**: 기술·아키텍처·패턴이 없을 때 발생할 구체적 결합도, 중복, 보안, 상태 불일치, 운영·협업 위험.
- **변경 근거**: 실제 수정 경로, 구현·리팩터링 방식, 적용 전후 구조와 동작.

대화에 없는 사용자 의도, 선택, 피드백을 만들지 않는다. 내부 추론을 노출하지 않고 대화에서 확인된 제안·선택과 코드·검증에서 관찰된 기술적 판단만 요약한다. 사용자 후속 피드백이 없으면 `없음`으로 기록한다.

## 사례 구조

각 독립 문제나 요구사항은 `## 사례 N — 제목`으로 분리하고 다음 항목을 모두 포함한다.

1. 메타데이터: 작업 유형, 관련 도메인/서비스, 문제 출처.
2. `### 문제 상황`: 사용자 요구·기획 변경·테스트 실패·구현 위험 중 실제 근거와, 미해결 시 발생할 문제.
3. `### 고민과 선택`: 사용자 제안, 에이전트 제안, 검토한 대안, 최종 선택과 제외 이유.
4. `### 적용`: 실제 구현·수정·리팩터링 경로와 동작.
5. `### 사용 기술과 구체적 목적`: 기술·구조·패턴별 해결하려는 문제와 적용 위치.
6. `### 결과`: 적용 전후 변화, 검증, 사용자 후속 피드백과 추가 요청.
7. `### 이력서·포트폴리오 문구`: 검증 가능한 짧은 이력서 bullet과 문제→고민→적용→결과 서술.

데이터·상태·협업 흐름이 바뀐 사례는 가능한 경우 Mermaid로 적용 전후 또는 최종 흐름을 도식화한다. 측정 가능한 성과는 실제 명령 결과와 수치만 사용한다.
