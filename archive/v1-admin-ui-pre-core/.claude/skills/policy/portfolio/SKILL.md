# Portfolio Log Policy

> 작업이 끝난 순간이 기억이 가장 선명하다.
> 구현/리팩터 완료 직후, 아래 구조로 경험을 기록해둔다.

---

## 언제 이 스킬을 사용하나요?

- 구현 또는 리팩터링 작업이 품질 검토 게이트를 통과한 직후
- 기술 면접 준비, 이력서 업데이트, 포트폴리오 정리 시
- "이 작업에서 뭘 고민했지?"를 나중에 떠올려야 할 때

---

## 1) 기록 위치

```
.claude/logs/portfolio/<YYYY-MM-DD>-<작업-슬러그>/portfolio-entry.md
```

예시:
```
.claude/logs/portfolio/2026-04-20-wallet-nft-holdings/portfolio-entry.md
```

---

## 2) 기록 구조 (필수 5개 섹션)

### 2-1. 문제 (Problem)

**무엇이 문제였는가.**

- 비즈니스/UX 측면의 문제와 기술 측면의 문제를 구분해서 서술
- "~가 없었다", "~가 불가능했다", "~가 느렸다" 형태로 구체적으로
- 측정 가능한 수치가 있다면 반드시 포함 (로딩 시간, 코드 중복 횟수 등)

```markdown
## 문제

- **비즈니스**: 관리자가 멤버의 지갑/NFT 보유 현황을 실시간으로 파악할 수 없었다.
- **기술**: MemberDetailModal이 단일 파일에 800줄이 넘었고,
  NFT 조회 로직이 컴포넌트 내부에 직접 인라인되어 있어
  재사용·테스트가 불가능한 구조였다.
```

---

### 2-2. 고민 과정 (Thought Process)

**어떤 선택지를 검토했고, 어떤 기준으로 판단했는가.**

- 검토한 접근법을 나열 (최소 2개 이상)
- 각 접근법의 trade-off를 명시
- 최종 판단 기준(성능/유지보수/일관성/일정 등)을 명시

```markdown
## 고민 과정

| 접근법 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| 기존 Modal에 NFT 섹션 추가 | 빠른 구현 | 파일 비대화 심화, 관심사 미분리 | ✗ |
| 별도 SideModal 분리 | 관심사 분리, 재사용 가능 | 상태 전달 설계 필요 | ✓ |
| 별도 페이지 라우팅 | 가장 명확한 분리 | UX 맥락 단절, 일정 초과 우려 | ✗ |

**판단 기준**: 모달 내 컨텍스트 유지(UX) + 컴포넌트 단일 책임(유지보수성) 우선.
```

---

### 2-3. 결과 (Results)

**무엇을 만들었는가.**

결과가 **단일**인 경우: 구현 내용과 핵심 코드 의사결정을 서술.
결과가 **복수**인 경우: 각 결과물을 나열하고 **왜 그 결과가 도출됐는지 이유를 명시**.

```markdown
## 결과

### 결과 1: WalletHoldingsPanel 컴포넌트 분리
- MemberDetailModal에서 지갑/NFT 보유 현황을 별도 SideModal 컴포넌트로 분리
- **도출 이유**: 모달 파일이 단일 책임 원칙을 위반했고,
  향후 다른 멤버 상세 화면에서도 동일 패널이 재사용될 가능성이 있었기 때문

### 결과 2: useFetchAdapter 기반 useWalletHoldings 훅 분리
- NFT 조회 로직을 커스텀 훅으로 추출하여 컴포넌트 외부로 이동
- **도출 이유**: 동일 데이터를 다른 화면(Dashboard 위젯)에서도 참조할 수 있어
  fetch 로직의 중복 방지가 필요했기 때문
```

---

### 2-4. 성과 (Impact)

**결과가 실제로 어떤 차이를 만들었는가.**

- 정량적 수치 우선 (파일 줄 수, 로딩 시간, 재사용 횟수 등)
- 수치가 없으면 정성적 평가라도 구체적으로 ("코드 리뷰 피드백 감소", "기획 변경 대응 속도 향상" 등)
- 팀/비즈니스 레벨의 영향을 서술할 수 있으면 포함

```markdown
## 성과

- MemberDetailModal 코드 줄 수: 820줄 → 340줄 (−59%)
- WalletHoldingsPanel은 이후 DashboardWidget에서 재사용됨 (중복 구현 0)
- 기획팀 요청으로 NFT 필터 기능 추가 시 useWalletHoldings 훅만 수정으로 대응 가능
```

---

### 2-5. 회고 (Retrospective)

**다시 한다면 무엇을 다르게 했겠는가. 또는 이 경험에서 얻은 인사이트.**

- 선택이 틀렸다면 솔직하게
- 잘된 부분도 기록 (면접에서 "잘한 점은?"에 답할 수 있게)
- 이 경험이 다음 작업에 어떤 영향을 줬는지

```markdown
## 회고

- SideModal 분리 결정은 맞았으나, 초기 설계 시 props 계약을 먼저 확정했더라면
  구현 단계에서 수정이 줄었을 것.
- 커스텀 훅 분리 패턴(useFetchAdapter 기반)을 이 작업에서 처음 적용했고,
  이후 프로젝트 전반의 표준 패턴이 됨.
```

---

## 3) 이력서/면접 전환 가이드

portfolio-entry.md를 이력서 문장으로 전환할 때 아래 공식을 사용한다.

```
[역할] + [행동] + [수치/결과] + [비즈니스 임팩트]
```

예시:
```
MemberDetailModal 리팩터링 시 NFT 보유 현황 패널을 별도 컴포넌트/훅으로 분리하여
코드 820줄을 340줄로 감소시켰고, 이후 Dashboard 위젯에서 재사용됨으로써
중복 구현 없이 신규 기능 대응 속도를 높임.
```

---

## 4) 금지

- 결과 섹션에 "~했다"만 기재하고 **왜** 그 결과가 도출됐는지 빠뜨리는 것
- 성과를 "좋아졌다", "빨라졌다" 같은 추상적 표현으로만 마무리하는 것
- 복수 결과를 단순 나열하고 각 결과의 **선택 이유**를 누락하는 것
- 회고 없이 성과만 기록하는 것 (면접에서 "어려웠던 점"에 답할 근거가 사라짐)
