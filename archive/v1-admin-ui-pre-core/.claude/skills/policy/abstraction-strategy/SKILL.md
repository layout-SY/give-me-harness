# Abstraction Strategy (Policy)

## 언제 이 스킬을 사용하나요?

- 컴포넌트/hook/유틸을 추출하거나 공용화 여부를 결정할 때
- 기존 자산에 추상화가 필요한지 판단할 때
- 추상화 수준(강한/약한)을 결정할 때
- closed vocabulary 설계(union type, column.type 등)의 변경 영향을 판단할 때

---

## 1. 계약(Contract) ≠ 추상화(Abstraction)

분리는 **계약을 자동으로 생성**한다. 추상화는 **의식적 작업**이다.

| 개념 | 정의 |
|---|---|
| **계약** | 시그니처 + 입출력 타입 + 호출 규약. 분리 즉시 자동 발생 |
| **추상화** | 계약 + 정보 은닉 + 불변식 + 대체 가능성. 의식적으로 설계해야 함 |

→ 함수를 분리했다고 추상화가 완성된 것이 아니다. 추상화 완성 척도: **"구현을 읽지 않아도 사용 가능한가"**

---

## 2. 추상화 4조건 — 비용이 정당화되는 경우

아래 조건 중 **하나 이상** 충족 시에만 추상화 작업 비용이 정당화된다. 하나도 충족하지 않으면 계약(시그니처)만으로 충분하다.

1. **소비자가 둘 이상** — 현재 호출처가 2개 이상
2. **구현이 둘 이상** — 환경별/정책별/전략별 구현 교체 가능성이 현재 또는 근미래에 존재
3. **불안정 영역에 안정 경계 필요** — 내부는 자주 바뀌지만 외부 계약을 유지해야 하는 경우
4. **인지 부하 감소 ROI** — 구현이 100줄 이상이면 호출처 1개여도 추상화 가치가 있음

---

## 3. 추상화 엄격도 결정 — 강한 vs 약한

### 강한 추상화가 필요한 경우

- 호출처가 자산을 **서로 독립적으로** 사용 (호출처끼리 모르는 관계)
- 자산이 **모듈 경계 밖**으로 노출됨 (공용 컴포넌트, 글로벌 hook)
- 계약 변경 시 **다수의 호출처에 파급**되는 구조

→ 제네릭, Discriminated Union, 전략 슬롯(callback), optional 필드로 차이를 contract 안에 흡수

### 약한 추상화로 충분한 경우

- 동일 모듈 내부 **helper 함수** (Table → commonCell 관계)
- 단일 호출처 전용 자산 (도메인 종속 hook)
- 조건: **상위 상태가 하위로 누설되지 않음** + **하위가 상위 특정 필드를 읽지 않음**

---

## 4. 추상화 엄격도 트리거

| 상황 | 조치 |
|---|---|
| 처음 분리 | 계약(시그니처 위생)만 챙김. 추상화 작업 불필요 |
| **두 번째 호출처 등장** | 도메인 hook → 공용 자산 승격 검토. 추상화 엄격도 올리는 시점 |
| 세 번째 이상 | 강한 추상화 적용. 제네릭/슬롯으로 차이 흡수 |

---

## 5. Closed Vocabulary 트레이드오프

`column.type`, status union 등 닫힌 어휘 집합을 설계할 때 적용한다.

| 변경 유형 | 계약 영향 | 호출처 영향 |
|---|---|---|
| **추가(additive)** | 계약 확장 | 없음 (옵트인) |
| **파괴(breaking)** | 기존 계약 깨짐 | 모든 호출처 강제 수정 |
| **행위(behavioral)** | 시그니처 동일, 동작만 변경 | 컴파일 통과하나 화면/로직이 조용히 변함 |

**어휘 추가 기준**: "둘 이상의 도메인이 정확히 같은 모양으로 쓰는가" — 한 도메인만 쓰면 `custom` 슬롯으로 외부화

**판별 한 줄**: 어휘 이름이 **"UI 형태의 이름"이면 안전**, **"도메인 개체의 이름"이면 누수**

---

## 금지

- 추상화 4조건 미충족 상태에서 선제적 추상화
- 단일 호출처 자산에 공용 계약 강제 적용
- closed vocabulary에 도메인 종속 어휘 추가 (→ custom 슬롯으로 분리)
- "미래에 쓸 수도 있으니" 이유의 추상화 (YAGNI)
