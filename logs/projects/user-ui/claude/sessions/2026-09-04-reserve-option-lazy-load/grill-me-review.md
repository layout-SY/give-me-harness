# Grill Me 검토

## Method Guardrails (검토 방법 안전장치)

- [x] neutral question-first 적용 여부 — 각 항목을 "이 구현이 왜 옳은가"가 아니라 "무엇을 근거로 어떤 대안을 배제했는가"로 먼저 물었고, 질문 문장에 답을 담지 않았다.
- [x] 질문이 검토자를 특정 구현 선택으로 유도하지 않는지 여부 — 질문에서 `onOpenChange`, `renderEmptyState`, `aria-busy` 같은 채택한 수단의 이름을 전제하지 않았다. Recommended Answer는 질문·답변·근거를 모두 기록한 뒤에 작성했다.

## Neutral Question Flow (중립 질문 흐름)

| 영역 | 중립적 질문 | 답변 | 근거 | Recommended Answer (권장 답변) |
| --- | --- | --- | --- | --- |
| 비활성 조건 | 사용할 수 없는 목록을 사용자에게 어떻게 알리기로 했고, 그 판단의 근거는 무엇인가 | 컨트롤 비활성화를 없애고 열린 목록 안의 필드별 문구로 바꿨다 | 기존 `isDisabled={disabled \|\| items.length === 0}`은 조회 전 목록이 항상 비는 지연 로딩에서 열림 자체를 막아 트리거가 발생하지 않는다. 비활성 컨트롤은 "왜 못 고르는지"를 말하지 못한다 | 현 구현 유지. 필드별 `emptyLabel`로 이유를 전달하고, 조회 실패·권한 등 다른 원인이 생기면 문구를 소비자가 바꿀 수 있게 열어 둔다 |
| 이전 데이터 표시 | 새 조회가 진행되는 동안 직전 목록을 어떻게 다루기로 했는가 | 조회 중에는 렌더하지 않고 로딩 문구만 보여 준다 | 예약 날짜를 바꾸면 이전 날짜의 시간 슬롯이 남는다. 그 사이 사용자가 선택하면 존재하지 않는 슬롯이 폼에 들어간다 | 유지. 체감 지연이 문제가 되면 stale-while-revalidate 표시를 어댑터 옵션으로 추가하는 편이 낫고, 기본값은 안전한 쪽이어야 한다 |
| 상태 노출 위치 | 조회 중 상태를 어느 요소에 어떤 속성으로 노출했고, 그 위치를 고른 근거는 무엇인가 | 트리거 버튼이 아니라 감싸는 요소에 `aria-busy`를 두었다 | 트리거에 붙였을 때 테스트에서 속성이 `null`로 나왔다. HeroUI `SelectTrigger`는 props를 RAC `Button`으로 넘기고 RAC가 `filterDOMProps`로 DOM 속성을 거른다 | 래퍼 유지. 어댑터가 HeroUI 내부를 우회 조작하는 것보다 비용이 낮고, 래퍼는 `width: 100%`만 갖는다 |
| 빈 상태 접근성 | 빈 상태·로딩 문구가 보조기술에 어떻게 전달되는지 확인했는가 | live region을 두지 않고 목록의 빈 상태 렌더에 맡겼다 | RAC가 빈 상태를 `role="option"`으로 감싼다(`react-aria-components/dist/private/ListBox.mjs:222`). 처음엔 `role="status"`를 넣었으나 listbox 옵션 안에 live region이 중첩되는 구조라 리뷰에서 제거했다 | 현 상태 유지. 조회 중 신호는 래퍼 `aria-busy`가 담당하고, 문구는 목록이 열릴 때 옵션으로 읽힌다 |
| 수정 범위 | 문제를 특정 화면에서 고칠지 공용 계층에서 고칠지 무엇을 기준으로 정했는가 | 팝업 폭과 드롭다운 계약 모두 공용 계층에서 고쳤다 | 팝업이 셸을 벗어나는 원인은 `dialog`의 top layer 렌더라 모든 팝업에 해당한다(`src/index.css:57`, `DESIGN.md:98`). 드롭다운도 예약 화면 15종이 같은 조회 패턴을 쓴다 | 공용 수정 유지. 영향 받는 다른 소비자는 `ReportPopup` 하나뿐이며 같은 셸 계약을 따른다. 사용자 확인을 거쳐 확정했다 |
| 역할 경계 | 라우트에 넣은 지연 로딩 흉내는 확인된 역할 경계 안에 있는가 | 경계선에 있다. TEMPORARY 미리보기로 한정했다 | 정책은 미리보기용 표시 상태를 허용하되 기능 로직으로 자라면 hook 계약을 제안하라고 규정한다. 파일 상단에 "실제 조회·취소·캐시는 hook·query 계층의 책임"을 명시했다 | 유지하되 Logic 인계 시 블록째 교체. 취소·경합을 흉내 내지 않은 것도 의도적이다 — 미리보기가 진짜처럼 보이면 교체가 늦어진다 |
| 중복 코드 | 같은 배선이 반복된 지점이 있는가, 지금 추상화하지 않은 이유는 무엇인가 | 드롭다운 3곳의 prop 배선이 3줄씩 늘었다 | 직전 세션이 "사용처 4번째에서 `ReservationSelectField` 추출"로 판단했고 사용처 수는 그대로다. 다만 반복 폭이 커져 추출 이득이 이전보다 크다 | 지금은 유지하되 `evaluation-log.md`에 옵션 소스 묶음(`{ items, isLoading, onOpen }`) 전환을 Logic 연결과 함께 처리하도록 기록했다 |
| 검증 충분성 | 무엇을 검증했고 무엇을 검증하지 못했는가 | lint·build·예약 테스트 10건은 통과했고, 실제 열림 흐름과 브라우저 렌더는 검증하지 못했다 | jsdom에서 RAC 팝오버 상호작용 테스트는 레이아웃 API 의존이 커 비용이 높다. 시각 QA는 사용자 요청이 있어야 수행한다. 전체 테스트 실패 6건은 직전 세션과 동일 목록이며 변경 파일과 import 연결이 없다 | 표현 계약(비활성 아님, `aria-busy`) 검증으로 남기고, 열림→조회 흐름은 Logic 역할의 hook 단위 테스트로 덮는다. 기준선 확인은 사용자에게 양도 |
