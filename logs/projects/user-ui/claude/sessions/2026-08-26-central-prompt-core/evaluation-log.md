# 평가 로그

## 현재 판정과의 경계

여기서는 Watcher 판정을 다시 평가하지 않는다.

## 감시 체계의 자기 검증

이번 세션에서 훅이 자기 세션의 `Stop` 을 차단했고, 그 과정에서 세 가지 결함이 드러났다. 주목할 점은 **결함이 사용자 보고나 코드 리뷰가 아니라 시스템 자신의 작동으로 발견되었다**는 것이다.

- 감시 규칙을 만든 주체가 그 규칙을 우회하고 있었다. 이 세션은 내내 `python3` 힙독으로 중앙 파일을 수정했고, 셸 리다이렉션 패턴만 보던 훅은 이를 감지하지 못했다. 규칙의 존재가 규칙의 적용을 보장하지 않는다.
- 호스트마다 감시 범위가 달랐다. Codex 는 매처 없이 전체 도구를 검사했고 Claude 는 편집 도구 넷만 검사했다. 같은 정책을 배포해도 집행 계층의 설정 차이가 실제 강제력을 가른다.
- 교정이 오탐을 낳았고, 그 오탐이 다시 정상 작업을 막았다. 감시 규칙을 좁히는 작업과 넓히는 작업은 항상 반대 방향의 비용을 만든다.

## 장기 관찰 사항

- 중앙화의 실패 지점은 도구 성능이 아니라 편집 지점의 이원화였다. `asan-harness`는 컴파일러, 어댑터, 권한 모델, 증거 체계를 갖췄으나 중앙에 프롬프트 본문이 없어 활성화되지 못했다. 이번 구현이 200줄대로 동작한 이유는 기능이 적어서가 아니라 원본 텍스트가 중앙에 실재하기 때문이다.
- 안전장치가 목표 달성을 봉쇄하는 패턴을 경계해야 한다. `asan-harness`는 프롬프트 파일 생성에 actual-host mutation certification을 요구했고, 설치된 세 호스트가 이를 통과할 수 없어 v0.1.3까지 릴리스하고도 한 글자도 반영하지 못했다. 요건은 목적에 비례해야 한다.
- 프롬프트는 세션 시작 시점에 적재되므로 실행 중 세션에 반영하는 방법은 없다. 변경 로그를 읽어 반영하는 방식은 부트스트랩 순환과 델타 재생 문제를 낳는다. 재시작을 전제한 현재 설계가 구조적으로 옳다.
- 호스트 간 강제력 비대칭이 품질 격차의 유력한 원인이었다. 동일 규칙을 두고 Codex만 종료 코드 2로 차단하고 Claude는 경고에 그쳤다. 규칙 문서를 통일하는 것만으로는 부족하며 집행 계층까지 통일해야 한다.

## 목록에 등록할 재사용 가능 자산

| 자산 | 위치 | 재사용 지점 |
| --- | --- | --- |
| `harness_core.py` | `asan-prompt-core/source/common/hooks/` | 종료 코드 기반 호스트 중립 훅. 새 호스트 추가 시 진입점만 작성하면 된다 |
| `sync.py`의 경로 매핑 구조 | `asan-prompt-core/bin/` | 공통·호스트 디렉터리 매핑과 SHA-256 매니페스트. 대상 추가는 `targets.json` 항목 추가만으로 끝난다 |
| 배너 주입 규칙 | `sync.py:rendered_bytes` | frontmatter 보존과 `*.template.md` 제외 처리 |

## 기술 부채

| 항목 | 내용 | 영향 |
| --- | --- | --- |
| 오버레이 부재 | 두 프로젝트가 완전히 동일한 프롬프트를 사용한다 | admin-ui에 없는 `npm run test`를 지시하는 등 사실과 어긋나는 지침이 발생한다 |
| 스킬 본문 빈약 | policy 15개 중 8줄 스킬이 8개다 | `review-checklist`가 Watcher 판정 기준으로 지목되나 근거가 부족하다 |
| OpenCode 미검증 | 플러그인 JS 어댑터를 실행 확인하지 못했다 | OpenCode 세션에서 차단이 동작하지 않을 수 있다 |
| 무결성 검증 축소 | 훅 파일 SHA-256 부트스트랩을 제거했다 | 훅 파일 변조를 훅 자체가 탐지하지 못한다. `sync.py check`가 부분적으로 대신한다 |
| `asan-harness` 방치 | 233파일 런타임이 사용되지 않은 채 남는다 | 어느 쪽이 정본인지 혼동할 여지가 있다 |

## 프로세스 개선 사항

- 프롬프트 자산 규모를 먼저 측정한 것이 설계 규모를 결정했다. 1,600줄이라는 수치가 없었다면 기존 런타임을 억지로 재사용했을 가능성이 크다. 도구를 만들기 전에 관리 대상의 크기를 재는 절차를 유지할 만하다.
- 사용자가 기준 프로젝트를 하나로 지정한 결정이 병합 비용을 없앴다. 양방향 병합이었다면 15개 스킬의 문장 단위 대조가 필요했다.

## 권고 사항

1. **오버레이 도입(우선)** — `targets.json`에 프로젝트별 치환 값과 추가 스킬 경로를 두어 명령어 목록과 기술 스택 사실을 프로젝트별로 분기한다. admin-ui의 `npm run test` 불일치가 이 기능의 최소 요건을 정의한다.
2. **스킬 본문 보강** — 외부 프롬프트를 참고해 8줄 스킬을 실사용 가능한 판정 기준으로 확장한다. `review-checklist`가 최우선이다.
3. **OpenCode 실동작 검증** — OpenCode 세션에서 관리 경로 편집을 시도해 차단을 확인하고, 실패 시 어댑터를 수정한다.
4. **`asan-harness` 처리 결정** — 보관, 아카이브, 삭제 중 하나를 선택해 정본 혼동을 없앤다.
5. **배포 커밋 규율** — 배포 결과를 각 프로젝트에 커밋해야 세션 시작 시점의 프롬프트가 확정된다. 커밋 없이 배포만 반복하면 작업 트리 상태에 따라 프롬프트가 달라진다.
