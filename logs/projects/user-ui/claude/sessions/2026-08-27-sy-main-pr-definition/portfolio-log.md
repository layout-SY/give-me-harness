# 이력서·포트폴리오 기록

## 사례 1 — main 대비 sy-main 작업 범위를 PR 정의서로 추합

- 작업 유형: 문서
- 관련 도메인/서비스: 사용자 UI (`asan-metaverse-user-ui`), 시민참여, 인증
- 문제 출처: 사용자 요구

### 문제 상황

- 사용자가 제시한 요구·문제·변경 이유: `main`과 비교해 `sy-main` 작업 내용을 정의하는 PR 문서가 필요했다.
- 테스트·런타임에서 관찰한 오류: 없음. 이 세션은 앱을 실행하지 않았다.
- 필요한 기술·구조·패턴이 없을 때 발생할 문제: 114커밋·314파일 diff를 묶지 않으면 리뷰어가 시민참여·인증·셸 변경을 한 덩어리로 오해하거나, 세션 로그 파일 수에 가려 앱 변경 규모를 잘못 읽는다.

### 고민과 선택

- 사용자 제안: `main` 대비 `sy-main` 작업 정의 PR 문서를 만든다.
- 에이전트 제안: `origin/main...sy-main`을 기준으로 기능 묶음·라우트 표·테스트 계획을 쓰고, 하네스 파일과 앱 파일을 숫자로 분리한다.
- 검토한 대안: (1) 파일 전체 나열 (2) `origin/sy-main`만 비교 (3) 미커밋까지 PR 범위에 포함
- 최종 선택: 로컬 `sy-main` HEAD 기준 기능 정의서. 미커밋은 제외하고 ahead 1커밋만 명시.
- 선택 이유와 제외한 방식의 이유: 사용자 요청은 작업 내용 정의다. 파일 나열은 읽기 어렵고, `origin/sy-main`만 쓰면 `586908c`가 빠지며, 미커밋은 사용자가 PR에 넣으라고 하지 않았다.

### 적용

- 변경 경로: `.codex/logs/sessions/2026-08-27-sy-main-pr-definition/`
- 구현·수정·리팩터링 내용: `pr-definition.md`와 필수 8종 작성. 앱 코드 없음.
- 핵심 동작: 리뷰어가 시민참여 라우트, loginId 세션, MSW `dev` 조건, `main` 대비 UX 변화를 한 문서로 볼 수 있다.

### 사용 기술과 구체적 목적

| 기술·구조·패턴 | 해결하려는 구체적 문제 | 적용 위치와 방식 |
| --- | --- | --- |
| three-dot diff (`origin/main...sy-main`) | merge-base 이후 커밋만 범위에 넣기 | `git log` / `git diff --stat` |
| FSD 경로 구분 (`features` vs `pages`) | 시민참여 파일을 한 덩어리로 오해하지 않기 | PR 본문 구조 절 |
| 앱 파일 / 하네스 파일 규모 분리 | 314파일 중 세션 로그가 규모를 부풀리는 문제 | Summary와 변경 규모 절 |

### 결과

- 적용 전: `sy-main` 작업 범위를 한곳에 모은 PR 본문이 없었다.
- 적용 후: 라우트·인증·MSW·제외 범위가 적힌 정의서가 세션 디렉터리에 있다.
- 검증 결과: 커밋 수 114, 전체 314/+16555/-568, 앱 169/+11783/-568을 명령 출력과 대조. 라우트·인증은 현재 소스와 대조. `npm` 검증은 실행하지 않음.
- 사용자 후속 피드백: 없음
- 추가 요청 및 남은 제한: PR 미생성. 로컬이 `origin/sy-main`보다 1커밋 앞섬.

### 이력서·포트폴리오 문구

- 이력서 bullet: 114커밋·314파일 브랜치를 `git` three-dot diff와 현재 라우트/인증 코드로 대조해, 시민참여·세션·MSW 범위를 한 PR 정의서로 추합했다.
- 포트폴리오 서술: `main` 대비 `sy-main` 리뷰 본문이 없어 작업 범위가 파일 수만으로 읽힐 위험이 있었다. 세션 로그와 앱 파일을 숫자로 나누고 라우트 표와 인증 계약을 현재 코드에서 확인한 뒤 정의서를 작성했다. 앱 코드는 바꾸지 않았고, 미커밋 변경은 PR 범위에서 제외했다.
