# 평가 로그

## 현재 판정과의 경계

여기서는 현재 변경의 PASS/FAIL을 다시 판정하지 않는다. 아래는 장기 관찰과 backlog 후보다.

## 장기 관찰 사항

- 회의 예약 도메인의 팝업이 STEP03·STEP04로 두 개가 되었고, 앞으로 STEP07(취소 확인), STEP08(취소 완료), STEP16(입장 거부), STEP19(입장 대기), STEP21(입장 안내)까지 최소 5개가 더 예정되어 있다. 현재는 각 팝업이 `.vo-complete` 클래스를 문자열로 공유하는 방식이라, 개수가 늘면 "완료"라는 이름과 실제 역할(공용 팝업 골격)의 괴리가 커진다.
- 팝업 제목 id가 파일마다 고정 문자열이다. 팝업이 늘수록 id 규칙을 사람이 기억해야 한다.
- Figma 문구를 컴포넌트 기본값으로 두는 방식이 STEP03·STEP04에서 반복되었다. 문구 변경이 발생하면 컴포넌트 파일을 열어야 한다.

## 이 문제가 중요한 이유

같은 화면 계열이 5개 이상 추가되는 것이 이미 확정된 로드맵이다. 골격 이름과 id 규칙을 지금 정리하지 않으면, 나중에 7~8개 파일을 한꺼번에 고쳐야 하는 일괄 리팩터링 비용이 생긴다.

## 재사용 가능 자산

- `NoticeBox`(title/emphasis/description/tone)는 두 팝업에서 형태 변경 없이 그대로 쓰였다. 안내 박스 계약으로 안정적이다.
- `.vo-complete` 골격(아이콘 원형 + 텍스트 블록 + 안내 박스 + 전폭 버튼)이 사실상 이 도메인의 표준 팝업 레이아웃이다.

## 기술 부채

- `.vo-complete`라는 의미 종속적인 클래스명이 공용 골격 역할을 하고 있다.
- 팝업 제목 id 하드코딩.
- 전체 테스트에 `citizen-participation` MSW 실패 6건이 상시 존재해, 신규 작업마다 "기존 실패인지" 판별하는 비용이 든다.

## 추상화·아키텍처·의존성 방향

- 의존 방향은 정상이다: `features/meeting-reservation/ui` → `shared/ui`, 역방향 참조 없음.
- 팝업이 상태를 갖지 않고 props/callback만 받는 구조라 Logic 계층 교체에 열려 있다. 이 경계는 유지할 가치가 있다.

## 프로세스 개선 사항

- 이번 세션에서 branch proposal의 산출물 scope를 날짜 기반 이름으로 추정해 넣었다가, launcher가 바인딩한 `ASAN_SESSION_DIR`과 달라 `update-scope`를 한 번 더 거쳤다. proposal 작성 전에 `ASAN_SESSION_DIR`을 먼저 확인하면 승인 라운드 1회를 줄일 수 있다.

## 권고 사항

1. 팝업이 3개째가 되는 시점에 `.vo-complete`를 `.vo-popup` 같은 중립 이름으로 바꾸고 STEP03·STEP04를 함께 옮긴다. 지금 단독으로 하면 이번 변경 범위를 넘는다.
2. 제목 id를 `useId()` 또는 props로 받는 방식으로 통일한다. 팝업 추가 시점에 한 번에 적용한다.
3. `citizen-participation` MSW 실패 6건을 별도 task로 처리한다.
