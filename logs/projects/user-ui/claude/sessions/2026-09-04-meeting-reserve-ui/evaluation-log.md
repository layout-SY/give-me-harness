# Evaluation Log

## Context
회의 예약 서비스의 첫 두 화면을 구현하면서 `src/features/meeting-reservation` 슬라이스를 신설했다. 남은 화면정의서 15종(STEP04~STEP24: 예약 제한 팝업, 예약 목록·상세, 취소 확인·완료, 입장코드 입력·확인, 입장 거부·대기, 참여자 현황, 기기 체크, 회의실 웹뷰, 퇴장 확인, 회의 종료)이 같은 슬라이스에 누적될 예정이므로 지금의 구조 결정이 장기 비용을 좌우한다. 아래는 현재 변경의 통과 여부(review-log)와 별개로 기록하는 구조적 개선 사항이다.

## Structural Risks
1. **화면 셸의 3중 중복 위험**
   `citizen-participation`(cp-)과 `meeting-reservation`(vo-)이 거의 동일한 셸·헤더·sticky 액션바·필드 그룹을 각자 갖고 있다. 세 번째 도메인이 추가되면 같은 CSS가 세 벌이 된다. `src/shared/ui/screen-shell`(Screen / ScreenHeader / BottomActionBar / Field)로 승격하고 두 슬라이스가 소비하도록 정리할 시점이 임박했다. 승격에는 CP 파일 소유권이 걸리므로 별도 scope 승인이 필요하다.

2. **`shared/ui/dropdown`의 index 기반 API**
   호출부마다 value↔index 변환 코드를 요구한다(이번 화면에서만 3회). 예약 목록 필터, 시간 슬롯 재선택 등 후속 화면에서 반복이 누적된다. value 기반 오버로드(`value`/`onValueChange`)를 추가하면 호출부가 사라진다. shared 어댑터 변경이므로 UI 역할 단독으로 결정할 사안이 아니다.

3. **미리보기 라우트 코드의 잔존 위험**
   `src/pages/meeting-reservation/ui/MeetingReserveRoute.tsx`의 옵션 상수와 참여자 샘플은 TEMPORARY다. Logic 역할이 예약 API를 붙일 때 교체되지 않으면 하드코딩된 테마·날짜 목록이 운영에 노출된다. 후속 화면도 같은 방식으로 미리보기를 만들면 위험이 화면 수만큼 늘어난다. 예약 옵션은 서버가 내려주는 값이라는 전제를 API 계약 단계에서 못 박아야 한다.

4. **예약 상태 표현의 분산**
   "승인대기"가 이번엔 팝업 안의 강조 텍스트로 구현됐지만, STEP05 예약 목록·STEP06 상세에서는 배지 형태가 필요할 가능성이 높다. 상태 라벨·톤 매핑을 각 화면이 따로 정의하면 표기가 갈라진다. 예약 상태 → 라벨/톤 매핑을 슬라이스 model 계층에 한 번만 두고 `shared/ui/status/status-badge`의 `StatusBadgeTone`으로 연결하는 것을 권한다.

5. **테스트가 표현 계약만 덮는다**
   현재 테스트는 문구·콜백·ARIA 속성을 검증하며 CSS 결과와 실제 상호작용 흐름(드롭다운 열기→선택)은 덮지 않는다. 화면이 15개로 늘면 "문구 존재" 테스트만 늘어나 회귀 탐지력이 떨어진다. 폼 상태 전이가 Logic 계층으로 옮겨간 뒤 hook 단위 테스트로 커버리지를 옮기는 편이 비용 대비 효과가 크다.

## Why This Matters
예약 흐름은 이번 두 화면으로 끝나지 않고 15개가 더 붙는다. 지금 슬라이스에 남기는 패턴(셸 복제, index 기반 Dropdown 호출부, 미리보기 상수, 상태 라벨 정의 위치)이 그대로 15회 복제되면, 나중에 되돌리는 비용이 화면 수에 비례해 커진다. 특히 1번과 2번은 지금 한 번 정리하면 이후 화면들이 자동으로 혜택을 받는 종류의 부채다.
