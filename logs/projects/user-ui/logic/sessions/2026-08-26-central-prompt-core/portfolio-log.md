# 이력서·포트폴리오 기록

## 사례 1 — 다중 프로젝트 AI 하네스 프롬프트 드리프트 제거

- 작업 유형: AI 하네스
- 관련 도메인/서비스: `asan-metaverse-user-ui`, `asan-metaverse-admin-ui` 공통 개발 환경
- 문제 출처: 사용자 요구

### 문제 상황

- 사용자가 제시한 요구·문제·변경 이유: 구조와 공용 컴포넌트가 거의 동일한 두 프로젝트가 시스템 프롬프트를 각각 보유한 탓에, 한쪽에서 개선한 스킬·훅·에이전트·`AGENTS.md`·`CLAUDE.md`가 다른 쪽에 반영되지 않아 동작이 갈라지고 산출물 품질이 현저히 차이났다. 어떤 모델(Codex, Claude Code, OpenCode)을 쓰든 동일한 프롬프트로 세션이 시작되는 중앙화 구조를 요구했다.
- 테스트·런타임에서 관찰한 오류: 두 프로젝트 스킬 15개 중 13개가 내용이 달랐고 한쪽에만 존재하는 스킬이 4개였다. `AGENTS.md`는 절 제목부터 전면 상이했다. 동일 규칙을 두고 Codex는 4개 훅이 종료 코드 2로 하드 차단하는 반면 Claude Code는 훅 디렉터리 자체가 없어 경고에 그쳤다.
- 필요한 기술·구조·패턴이 없을 때 발생할 문제: 편집 지점이 프로젝트마다 존재하는 한 드리프트는 재발한다. 규칙 문서만 통일하고 집행 계층을 통일하지 않으면 호스트별 품질 격차도 남는다.

### 고민과 선택

- 사용자 제안: 별도 중앙 프롬프트 프로젝트를 만들되, 대안으로 변경 로그 문서를 남기고 각 세션이 시작 시 이를 읽어 컨텍스트에 반영하는 방식을 검토했다.
- 에이전트 제안: 변경 로그 방식의 세 가지 결함을 제시했다. 로그를 읽으라는 지시 자체가 동기화 대상 프롬프트에 있어야 하는 부트스트랩 순환, 델타 재생이 원본 열람보다 부정확한 상태 복원 문제, 모델의 자발적 준수에 의존해 강제력이 없다는 점이다. 중앙 원본을 두고 세션 시작 시 파일로 주입하는 방식을 권고했다.
- 검토한 대안: (1) 기존 `asan-harness` Python 런타임 재사용, (2) git submodule 또는 symlink 마운트, (3) 신규 경량 도구 작성.
- 최종 선택: 신규 경량 도구. 기존 런타임은 재사용하지 않았다.
- 선택 이유와 제외한 방식의 이유: 코드 조사 결과 `asan-harness`는 v0.1.3까지 릴리스되었음에도 중앙에 프롬프트 본문이 없었다. `governance_sources.py`가 `"AGENTS.md#6"` 같은 앵커 참조만 보유하고, `governance_render.py`의 `_root()`가 생성하는 `AGENTS.md`는 10줄 메타데이터 스텁이며 `render_command`가 이를 `os.replace`로 덮어쓰는 구조였다. 실행하면 지침이 소실된다. 또한 프롬프트 파일 생성에 actual-host mutation certification을 요구해 설치된 세 호스트 중 어느 것도 통과할 수 없는 자기 봉쇄 상태였다. 반면 관리 대상 프롬프트는 1,600줄에 불과했고, `.agents/skills/`가 세 호스트 공통 경로여서 396줄이 무변환 복사 대상임을 확인해 260줄 도구로 충분하다고 판단했다.

### 적용

- 변경 경로: `~/SynologyDrive/asan-prompt-core/**`(신규), `AGENTS.md`, `CLAUDE.md`, `.agents/skills/**`, `.codex/**`, `.claude/**`, `.opencode/**`, `.harness/roles/**`
- 구현·수정·리팩터링 내용: 사용자가 지정한 기준 프로젝트의 프롬프트에서 내부 모순 8건을 먼저 교정한 뒤 중앙 저장소로 이관했다. 공통 원본과 호스트별 원본을 분리하고, 경로 매핑 복사와 SHA-256 매니페스트만 수행하는 배포 도구를 작성했다. 호스트 중립 판정 로직 하나에 얇은 진입점을 붙이는 방식으로 세 호스트 훅을 구현했다.
- 핵심 동작: 중앙에서 편집 후 `deploy`하면 두 프로젝트에 동일 파일이 배포된다. 프로젝트 안에서 관리 경로를 편집하려 하면 훅이 종료 코드 2로 차단하고 중앙 대응 경로와 재시작 절차를 안내한다. `check`가 프로젝트 측 임의 수정을 해시로 탐지한다.

### 사용 기술과 구체적 목적

| 기술·구조·패턴 | 해결하려는 구체적 문제 | 적용 위치와 방식 |

| 단일 진실 원천 | 편집 지점 이원화로 인한 드리프트 재발 | `source/`를 유일한 편집 지점으로 두고 프로젝트 측 편집을 훅으로 봉쇄 |

| frontmatter 보존 배너 주입 | 배너가 YAML frontmatter를 깨뜨리는 문제 | frontmatter 종료 위치를 찾아 그 뒤에 삽입하고 `*.template.md`는 제외 |

### 결과

- 적용 전: 두 프로젝트가 각자 프롬프트를 보유했고 스킬 15개 중 13개가 상이했다. 호스트별 강제력이 달라 Codex만 규칙이 집행되었다.
- 적용 후: 관리 대상 129개 파일이 두 프로젝트에서 해시 수준으로 동일하다. 세 호스트가 같은 판정 코어를 공유한다.
- 검증 결과: 훅 단위 테스트 9종 통과. `check --target all`이 양쪽 모두 정합 129개 보고. MANIFEST 대조에서 경로 집합 동일, 해시 불일치 0건. 관리 경로 편집 시도 exit 2, 비관리 경로 exit 0. 임의 수정 후 `check` exit 1, 재배포로 복구. `npm run lint`와 `npm run build` 통과. `npm run test`는 209건 통과, 2건 실패이며 해당 실패는 애플리케이션 코드를 변경하지 않았음이 `git status`로 확인된 사전 존재 실패다.
- 사용자 후속 피드백: 없음
- 추가 요청 및 남은 제한: 프로젝트 고유 오버레이 미지원으로 admin-ui에 존재하지 않는 `npm run test`를 지시하는 불일치가 남는다. OpenCode 플러그인 어댑터는 실행 검증하지 못했다.

```mermaid
flowchart LR
  Before[프로젝트별 프롬프트 사본<br/>스킬 15개 중 13개 상이<br/>호스트별 강제력 비대칭] --> Change[중앙 단일 원본<br/>해시 매니페스트 배포<br/>호스트 중립 훅 코어]
  Change --> After[129개 파일 해시 동일<br/>편집 시도 종료 코드 2 차단<br/>drift 자동 탐지]
```

### 이력서·포트폴리오 문구

- 이력서 bullet: 두 프런트엔드 프로젝트에 분산되어 있던 AI 에이전트 시스템 프롬프트를 중앙 저장소로 통합하고, 해시 기반 배포·검증 도구와 3개 호스트 공용 편집 차단 훅을 구현해 관리 대상 129개 파일의 완전 일치와 드리프트 자동 탐지를 달성했다.
- 포트폴리오 서술: 구조가 유사한 두 프로젝트가 시스템 프롬프트를 각각 보유해 한쪽의 개선이 다른 쪽에 반영되지 않는 드리프트가 발생했고, 스킬 15개 중 13개가 상이한 상태였다. 기존에 구축된 233파일 규모의 Python 하네스 런타임 재사용을 먼저 검토했으나, 코드 조사 결과 중앙에 프롬프트 본문이 없고 렌더러가 실제 지침을 10줄 스텁으로 덮어쓰며 활성화 요건이 스스로를 봉쇄하는 구조임을 확인해 배제했다. 대신 관리 대상이 1,600줄이고 세 호스트가 스킬 경로를 공유한다는 측정 결과에 근거해 260줄 규모의 경량 도구를 선택했다. 단일 진실 원천과 SHA-256 매니페스트로 배포·검증을 구성하고, 호스트별 출력 규격 차이를 종료 코드 프로토콜로 흡수해 판정 로직 하나를 세 호스트가 공유하도록 설계했다. 그 결과 129개 파일이 해시 수준에서 동일해졌고, 프로젝트 측 임의 편집은 차단되며 드리프트는 자동으로 탐지된다.

## 사례 2 — AI 에이전트 역할 경계 설계와 테스트 가능성의 동형성 발견

- 작업 유형: AI 하네스
- 관련 도메인/서비스: 중앙 프롬프트 시스템의 역할 범위 세션(`--role`) 설계 연구
- 문제 출처: 사용자 요구

### 문제 상황

- 사용자가 제시한 요구·문제·변경 이유: 런처에 `--host` 뿐 아니라 `--role` 을 더해 세션마다 담당 범위를 지정하는 방안을 검토하려 했다. 사용자가 직접 두 가지 난점을 제시했다. Claude 가 `ui` 역할인데 CSS 를 제어하는 JavaScript 를 수정하는 경우, Codex 가 `generator` 역할인데 React 컴포넌트 안의 `onClick` 액션 함수를 수정하는 경우다. 경계 정의의 복잡도가 높아 도입을 보류하되 연구와 문서화를 요청했다.
- 테스트·런타임에서 관찰한 오류: 없음. 설계 단계의 연구다.
- 필요한 기술·구조·패턴이 없을 때 발생할 문제: 경계를 정의하지 못한 채 강제하면 정상 작업이 차단되어 시스템 신뢰를 잃는다. 반대로 강제를 포기하면 역할 구분이 프롬프트상의 선언에 그쳐 병렬 세션 간 충돌을 막지 못한다.

### 고민과 선택

- 사용자 제안: 역할별 감시 범위를 정의하되 경계 복잡도가 높으므로 도입은 나중으로 미루고, 연구 결과를 문서로 남긴다. 이후 검증 결과를 보고 "관심사 분리가 테스트 용이성을 높이듯 AI 동작 감시 훅 작성도 용이하게 만든다"는 해석을 제시했다.
- 에이전트 제안: 경로 기반 강제, diff 위치 기반, 선언 기반, 관측 후 귀납의 네 가지 접근을 비교하고 관측 우선 방식을 권고했다.
- 검토한 대안: 경계를 먼저 정의하고 즉시 차단하는 방식. 정의할 근거 데이터가 없어 오판이 불가피하다고 판단해 제외했다.
- 최종 선택: 강제와 관측을 분리하여 Phase 0(역할 주입) → Phase 1(관측) → Phase 2(경고) → Phase 3(선택적 차단)으로 단계화하고, 도입 판단 기준과 미해결 질문을 함께 문서화했다.
- 선택 이유와 제외한 방식의 이유: 저장소의 실제 코드가 경로만으로 판정 불가능함을 보여주었기 때문이다. `src/features/auth/ui/LoginPage.tsx` 와 `src/features/meeting/ui/MeetingPage.tsx` 는 같은 `src/**/ui/**` 경로에 있으나, 전자는 모든 상태와 동작을 props 로 주입받아 도메인 지식이 없고 후자는 `useState` 6개, `useApi()`, `useAgoraMeeting()`, 비동기 RTC 자격 증명 갱신을 포함한다. 후자를 `ui` 로 판정하면 로직 수정을 허용하고 `logic` 으로 판정하면 UI 수정을 막는다. 어느 쪽으로도 틀린다.

### 적용

- 변경 경로: `~/SynologyDrive/asan-prompt-core/docs/role-scoped-sessions.md`(신규 254줄), `README.md`(연구 문서 등록)
- 구현·수정·리팩터링 내용: 경계 붕괴 지점을 저장소 실제 코드로 특정하고, 접근법 네 가지를 비교한 뒤 단계적 도입안, 역할별 판정 규칙 초안, 구현 스케치, 도입 판단 기준, 미해결 질문을 정리했다. 이후 테스트 가능성과 감시 가능성의 관계를 검증하여 8.1절로 추가했다.
- 핵심 동작: 판정 규칙 표에 `명백히 소유`, `명백히 비소유` 와 함께 `판정 보류` 열을 두었다. 사용자가 제시한 두 난점이 정확히 이 열에 해당하며, 이 열을 없애려 하지 말고 여기 쌓이는 사례를 관측하라는 것이 제안의 요지다.

### 검증 과정과 가설 수정

최초 가설은 "관심사가 섞인 파일은 테스트하기 어려우므로 테스트가 없을 것"이었다. 데이터는 반대였다.

| 파일 | 로직 마커 | 테스트 파일 |
| --- | --- | --- |
| `MeetingPage.tsx` | 22건 | 있음 |
| `LoginPage.tsx` | 0건에 가까움 | 없음 |

테스트 유무가 용이성이 아니라 필요성을 반영한다고 판단하여 지표를 테스트 코드의 모킹 부담으로 교체했다. `MeetingPage.test.tsx` 는 125줄 중 모킹과 셋업이 18줄이고 실제 단언은 2건이며, 2건을 검증하기 위해 6개 모듈을 `vi.mock` 한다. 그 여섯은 `use-api`, `meetingAccess`, `meetingForms`, `useAgoraMeeting` 과 하위 UI 두 개로, `api`·`model`·`hook` 경로다. 이는 연구 문서 6절에서 `logic` 역할 소유로 정의한 경로와 일치한다.

즉 개발자가 테스트를 작성하며 그은 모킹 경계와 역할 시스템이 그으려는 경계가 같은 지점이었다.

### 사용 기술과 구체적 목적

| 기술·구조·패턴 | 해결하려는 구체적 문제 | 적용 위치와 방식 |
| --- | --- | --- |
| 강제와 관측의 분리 | 경계 정의 근거가 없는 상태에서 차단하면 오판이 불가피하다 | Phase 0~3 단계화. 관측 데이터로 규칙을 조정한 뒤에만 차단으로 승격 |
| `판정 보류` 범주 | 이분법으로 분류할 수 없는 사례를 억지로 배정하면 오판이 된다 | 판정 규칙 표에 제3의 열을 두어 미결 사례를 명시적으로 보관 |
| 로직 마커 휴리스틱 | 경로만으로 혼재 여부를 알 수 없다 | `useState`, `use<도메인>()`, `async`, `execute(` 등의 출현 빈도로 혼재도 추정. 실제 코드에서 22건 대 0건의 구분력 확인 |
| 모킹 목록 기반 경계 추출 | 휴리스틱보다 정확한 경계 근거가 필요하다 | 기존 테스트의 `vi.mock` 대상을 집계하여 개발자가 실제로 그은 경계를 추출 |
| 부수 효과의 자산화 | 강제력을 갖기 전까지 도입 가치가 없어 보인다 | 역할 충돌 빈도 상위 파일을 리팩터링 후보 목록으로 활용 |

### 결과

- 적용 전: 역할 구분이 프롬프트상의 선언에 그쳤고, 경계를 어떻게 정의할지에 대한 판단 근거가 없었다.
- 적용 후: 경계 붕괴 지점이 저장소 실제 코드로 특정되었고, 단계적 도입안과 도입 판단 기준이 문서로 확정되었다. 테스트 코드의 모킹 목록이라는 즉시 사용 가능한 경계 추출 수단을 확보했다.
- 검증 결과: `MeetingPage.test.tsx` 의 `vi.mock` 6건이 모두 `api`·`model`·`hook` 경로이며 연구 문서의 `logic` 역할 정의와 일치함을 확인했다. 로직 마커 지표가 두 파일에서 22건 대 0건으로 구분력을 보였다. 최초 가설이 데이터로 반증되어 지표를 교체하는 과정을 거쳤다.
- 사용자 후속 피드백: 관심사 분리가 테스트 코드 작성을 용이하게 하듯 AI 동작 감시 훅 작성도 용이하게 만든다는 해석을 제시했고, 이를 문서와 본 기록에 반영하도록 요청했다.
- 추가 요청 및 남은 제한: 모킹 경계는 역할 경계의 하한이며 상한이 아니다. 한 파일 안에 JSX 와 핸들러 본문이 공존하는 경우는 모킹으로 갈라지지 않는다. 세 호스트의 역할 배분이 확정된 뒤 재검토한다.

```mermaid
flowchart LR
  Problem[경로만으로 역할 판정 불가<br/>같은 ui 경로, 다른 관심사] --> Insight[테스트 모킹 경계 = 역할 경계<br/>둘 다 경계 명시성으로 환원]
  Insight --> Result[단계적 도입안 확정<br/>모킹 목록으로 경계 추출<br/>충돌 빈도를 리팩터링 신호로]
```

### 이력서·포트폴리오 문구

- 이력서 bullet: AI 에이전트의 역할별 작업 범위 강제 방안을 연구하여, 관심사가 혼재된 파일에서 경로 기반 판정이 불가능함을 실제 코드로 규명하고 관측 우선의 단계적 도입안을 설계했다. 테스트 코드의 모킹 경계가 역할 경계와 일치함을 검증하여 별도 데이터 수집 없이 경계를 추출하는 방법을 확보했다.
- 포트폴리오 서술: 멀티 에이전트 시스템에서 세션마다 담당 범위를 강제하려 했으나, 같은 `src/**/ui/**` 경로의 두 컴포넌트가 서로 다른 성격을 갖는다는 점에서 경로 기반 판정의 한계에 부딪혔다. 한쪽은 모든 동작을 props 로 주입받아 도메인 지식이 없었고 다른 쪽은 인증 상태와 RTC 자격 증명 갱신을 포함했다. 경계를 먼저 정의하고 강제하는 순서로는 오판이 불가피하다고 판단해, 강제와 관측을 분리하여 관측 데이터로 규칙을 도출한 뒤 확실한 항목만 차단으로 승격하는 4단계 도입안을 설계했다. 검증 과정에서 최초 가설이 데이터로 반증되어 지표를 테스트 유무에서 모킹 부담으로 교체했고, 그 결과 테스트가 모킹하는 대상과 역할이 나뉘어야 하는 경계가 동일한 지점임을 확인했다. 이는 관심사 분리라는 기존 설계 원칙이 테스트 용이성과 AI 감시 가능성을 동시에 만족시킨다는 뜻이며, 새 제약을 도입하지 않고도 감시 체계를 세울 수 있는 근거가 되었다.
