# 예약 상세 후속 평가

## 결론과 현재 판정 경계

현재 변경은 수동 Watcher PASS이고 승인된 세 동작의 검증을 완료했다. 아래 내용은 장기 관찰 및 제안이며 이번 변경의 결함 판정을 대체하지 않는다.

## 관찰한 사실

- 상세 DTO는 기존 화면 명세 기반 추정 계약이며 strictObject를 사용한다. 서버 필드가 바뀌면 파싱 경계도 함께 바뀌어야 한다.
- 기존 controlled UI의 안내 props를 재사용해 feature UI 수정 없이 예약별 안내를 표시했다.
- 제한 조회의 캐시 상태와 폼 로컬 상태가 연결돼 있어 초기 조회와 배경 조회를 구분하는 것이 입력 보존에 직접 영향을 준다.
- 현재 빌드는 성공했으나 minified JavaScript 청크가 2,495.72 kB로 500 kB 경고 기준을 초과했다. 이 변경으로 증가한 크기라고 측정하지는 않았다.

## 장기 선택지와 권장 backlog

| 제안 | 채택하지 않을 때 남는 문제 | 추가 복잡성·비용 | 권장 시점 |
| --- | --- | --- | --- |
| 서버 확정 상세 계약과 nullable 안내 필드 대조 | 실제 응답과 추정 DTO가 다르면 상세 파싱 실패 가능 | 서버 담당자와 계약 검토 및 fixture·테스트 갱신 | 서버 계약 확정 시 |
| 서버 상태를 조회하는 다른 폼에서 isFetching 조건 조사 | 비슷한 화면이 있다면 배경 조회 입력 소멸이 남을 수 있음. 현재 다른 화면 결함을 확인한 것은 아님 | 별도 조사 범위와 동작 검증 필요 | 유사 보고나 후속 개선 승인 시 |
| 라우트·기능 청크 분할 분석 | 현재 큰 청크 경고가 계속 남음 | 라우팅·배포 캐시·로딩 흐름의 영향 분석 필요 | 별도 성능 측정 후 |

## 아키텍처와 재사용

전송 DTO → parser의 표시 값 → route props → controlled UI 방향을 유지했다. 이 작업만을 위해 공용 안내 adapter나 폼 상태 저장소를 만들 근거는 없다. 기존 MSW handler 주입 옵션과 QueryClient invalidation 테스트는 예약 도메인에서 재사용 가능하다. 새로운 추상화를 먼저 만드는 방식은 권장하지 않는다.

## 다음 단계

부모 담당자가 최신 자식 커밋과 handoff를 검토하고 승인된 완료 계약으로 통합한다. 사용자 후속 피드백은 아직 없다.
