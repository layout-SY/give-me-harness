# Grill Me 검토

## Method Guardrails (검토 방법 안전장치)

- [x] neutral question-first 적용 여부: 사용자 결정이 필요한 닫기 목적지를 열린 질문으로 먼저 확인했다.
- [x] 질문이 검토자를 특정 구현 선택으로 유도하지 않는지 여부: 정책·계약·실행 근거를 기준으로 답변했다. 권장안과 사용자 확정을 구분했다.

## Neutral Question Flow (중립 질문 흐름)

| 영역 | 중립적 질문 | 답변 | 근거 | Recommended Answer (권장 답변) |
| --- | --- | --- | --- | --- |
| 닫기 동작 | 제한 팝업을 닫으면 어디로 이동해야 하는가? | 사용자가 `/meeting`을 지정했다. | 현재 대화와 로비 복귀 회귀 테스트. | 지정 목적지로 이동하고 재진입 제한 검사 유지. |
| 안내 데이터 | 상세 안내를 표시하는 데 어떤 데이터가 필요한가? | 예약별 제목과 본문이 모두 필요하다. | 기존 UI props와 DTO 누락, 수정 전 HTTP·UI 테스트 실패. | nullable DTO를 parser의 표시 문자열과 연결. |
| 빈 값 | 안내 필드가 null이거나 한쪽만 있으면 어떻게 표시하는가? | 기존 UI 계약상 완성된 안내가 없으므로 안내 상자를 생략한다. | null·한쪽 누락·공백 4개 라우트 케이스 통과. | 공백을 정리하고 유효한 두 값만 props로 전달. |
| 상태 전환 | 제한 정보를 다시 조회하면 폼의 생명주기가 어떻게 달라지는가? | 이전 구현은 isFetching마다 폼을 제거했다. 수정 후 조회 중에는 유지하고 실제 restricted 결과에서만 제한 팝업으로 전환한다. | 수정 전 input 소멸 재현, 수정 후 false·true 결과 테스트 통과. | 초기 isPending과 배경 조회를 구분. |
| 계약 확정 | 서버 계약이 확정됐는가? | 아니다. 기존 API 파일에 화면 기반 추정 계약이라고 명시돼 있다. | 상세 DTO 주석과 원본 handoff. | 확정 서버 명세를 받을 때 두 nullable 필드와 표시 매핑을 대조. |

## 결론

사용자 지정 동작과 인계의 후속 3건을 승인된 Logic 경계 안에서 처리했다. 기존 UI·hook 계약을 재사용했고 추상화나 새 의존성을 추가하지 않았다. 예약 테스트 81개, lint, 타입·build가 통과했다. 부모 병합은 별도 승인과 부모 소유권에 따른다.
