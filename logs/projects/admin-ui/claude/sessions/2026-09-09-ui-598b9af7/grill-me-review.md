# 자기 반박 검토

## Q. 로그인 화면을 만들면서 라우트 보호를 하지 않으면 의미가 있나?

부분적으로 있다. 이번 변경이 실제로 해결하는 것은 "헤더 로그아웃 → 존재하지 않는 `/sign-in` 으로 이동" 이라는 확실한 결함과,
로그인 UI 자체의 부재다. 접근 제어는 `PrivateRoute` 연결(B안)이 별도로 필요하며 이번 범위에 포함하지 않았다.
**따라서 이 변경만으로 관리자 화면이 보호되지 않는다.** 후속 작업으로 남긴다.

## Q. 인증 실패 메시지를 전역 다이얼로그가 이미 처리하지 않나?

아니다. `use-api.tsx` 의 `handleFailure` 는 `onError` 가 주어지면 `errorPresentation: "silent"` 로 보고한다.
`useAuth.getAuthentication` 은 `onError` 에서 예외를 다시 던지므로 전역 다이얼로그 경로를 타지 않는다.
실제 코드를 읽고 확인했으며, 인라인 메시지는 중복 표시가 아니다.

## Q. 401 을 그대로 노출하지 않고 뭉뚱그리면 사용자가 원인을 못 찾지 않나?

의도한 선택이다. 아이디 존재 여부를 구분해 노출하면 계정 열거가 가능해진다.
대신 전송 실패(`transport`)와 401/403 이 아닌 서버 오류는 구분해 안내하므로,
"서버가 죽은 것" 과 "자격 증명이 틀린 것" 은 화면에서 구별된다.

## Q. 비밀번호가 잠깐 평문으로 렌더되지 않나?

`shared/ui/text-input` 은 `_isShow` 초기값이 `true` 이고 `useEffect` 에서 `enableShow` 를 보고 `false` 로 바꾼다.
따라서 최초 커밋 시점에 `type="text"` 로 한 프레임 렌더된다. 다만 그 시점의 값은 항상 빈 문자열이라 노출되는 내용은 없다.
이는 공용 컴포넌트의 기존 동작이고 다른 화면에도 동일하게 적용되므로 이번 scope 에서 고치지 않았다(개선 항목으로 기록).

## Q. 제출 버튼이 `disabled` 면 Enter 제출이 막히지 않나?

`canSubmit` 이 거짓인 경우는 (1) 아이디·비밀번호가 비어 있을 때, (2) 제출 중일 때뿐이다.
두 경우 모두 제출되지 않는 것이 올바른 동작이고, 두 필드가 채워지면 버튼이 활성화되어 Enter 암시적 제출이 성립한다.

## Q. UI 역할 경계를 넘지 않았나?

controller hook 은 입력 상태·제출 트리거·표시용 오류 문구 변환만 담당하고,
API 호출·토큰 저장·세션 상태 전이는 전부 기존 `useAuth` / `auth-session` 에 남아 있다.
`entities`, `features/auth`, `shared/api` 는 읽기만 했고 수정하지 않았다.

## Q. 새 색상이나 폰트를 추가했나?

없다. `_variables.css` 와 `_cp-admin.css` 에 이미 정의된 토큰만 참조했고, 하드코딩한 색상 값은 없다.
