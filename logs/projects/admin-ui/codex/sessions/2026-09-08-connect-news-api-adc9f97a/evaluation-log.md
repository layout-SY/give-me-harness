# 평가 기록

## 현재 판단

ApiClient·도메인 DTO/parser·query/mutation·폼 표시 모델을 분리해 기존 실 API 패턴과 일관성을 확보했다. 새 공용 추상화나 패키지를 도입하지 않았다. 평가는 검증 PASS를 대신하지 않는다.

| 후속 권고 | 채택하지 않을 때 남는 실제 문제 | 채택 시 추가되는 작업·복잡성 |
| --- | --- | --- |
| 공지 목록에서 숫자 newsId로 수정 라우트 연결 | 현재 NT-형식 mock 목록에서 실제 공지 수정으로 이동할 수 없다 | 혼합 게시글과 news의 목록 책임, 필터·집계 UI를 정해야 한다 |
| 유형·상단고정·등록 UI 연결 | 공개 API/hook은 있어도 해당 조작 UI가 없다 | 유형·게시 상태·상단고정 입력과 등록 성공 후 목록 이동 계약이 필요하다 |
| 기간·메인 노출 UI 정리 | 미지원 표시 및 날짜 입력 시 안내가 기존 레이아웃에 남는다 | UI 역할에서 입력 제거/읽기 전용 표현과 popup·미리보기 설명을 함께 조정해야 한다 |
| 서버 고정 항목 집계 계약 확인 | UI 후속 단계에서 일반/고정 집계 해석이 불확실하다 | 백엔드와 집계 정의를 합의하고 별도 UI mapper를 작성해야 한다 |
| 전체 lint 부채 처리 | 68개 오류 때문에 전체 lint 성공을 완료 근거로 사용할 수 없다 | 승인 범위를 넓히거나 독립 task로 오류를 수정하고 전체 회귀 검증해야 한다 |

## 근거와 제한

현재 코드를 정적으로 확인하고 Axios·MSW 및 QueryClient 테스트를 실행했다. 실서버와 브라우저 조작은 검증하지 않았다. 서버 처리량·성능 개선·운영 성과 수치를 추정하지 않는다.
