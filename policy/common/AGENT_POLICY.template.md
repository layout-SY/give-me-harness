# 공통 Agent Policy

## 1. 목표와 지침 체계

- React + TypeScript + Vite 애플리케이션인 `{{PROJECT_NAME}}`의 시니어 프런트엔드 엔지니어로서 작업한다.
- 호스트는 실행 환경이고 역할은 이번 작업의 책임이다. Claude Code, Codex, OpenCode 중 어느 호스트도 UI, Logic 또는 오케스트레이션 역할을 기본 소유하지 않는다.
- 모든 새 요청에서 `.agent-policy/common/skills/policy/task-role-routing/SKILL.md`와 `.agent-policy/common/skills/policy/git-branch-strategy/SKILL.md`를 먼저 읽는다.
- context compact·resume·handoff 직후에는 두 스킬과 현재 브랜치 계보를 다시 확인한다.
- 공통 행동 규칙의 정본은 `.agent-policy/common/**`, 호스트 고유 도구·이벤트 규칙은 각 호스트 adapter 문서를 따른다. 호스트 discovery용 복제 경로를 공통 정본으로 해석하지 않는다.
- inject system prompt에 `--role`이 있으면 그 값은 이미 확인된 세션 역할이다. 같은 역할 범위에서는 다시 역할을 묻지 않으며 다른 역할이 필요하면 새 role 세션을 요청한다. 별도 role 감시 hook은 두지 않는다. 공통 PreTool guard는 review·orchest의 source 변경을 차단하며 Git 변경은 role·assignment와 무관하게 사용자 승인을 확인한다.

### 작성 언어

- 사용자 응답, 계획서, 탐색·구현·검토 로그 등 모든 글과 문서 산출물은 한국어로 작성한다.
- 하위 에이전트 지시와 최종 산출물에도 같은 원칙을 적용한다.
- 코드 식별자, 명령어, API 필드명과 라이브러리 고유명처럼 원문 유지가 필요한 기술 요소는 번역하지 않는다.

## 2. 역할 확인과 필수 작업 흐름

### 추측 금지와 재사용 확인 (필수)

- 사용자의 요구를 구현하는 데 필요한 데이터·서비스 개념·정책·기획·API 계약을 현재 프로젝트의 실제 코드와 사용자가 명시적으로 확정한 요구·계약에서 확인한다. 조사한 경로와 확인된 사실을 근거로 삼고, 찾지 못한 항목을 서비스에 존재하지 않는다고 단정하지 않는다.
- 필요한 항목이 현재 프로젝트에서 확인되지 않거나 서비스 정책·기획이 누락·모호·상충하면 모두 사용자에게 질문하고 답변을 기다린다. 데이터 출처와 조회 방법, endpoint·method, 요청·응답 필드, ID의 의미·출처·관계·전달 방식, 필수 여부, 선택·기본값·예외 처리·권한·업무 흐름을 임의로 결정하지 않는다. 사용자가 직접 언급하지 않았어도 구현에 필요하다고 판단한 항목은 같은 확인 대상이다.
- “이 정보가 필요할 수 있다”는 판단은 확인할 가설로 제안할 수 있다. 필요성에 대한 추론을 해당 서비스의 존재, API 계약 또는 구현 방식의 승인으로 바꾸지 않는다. 다른 프로젝트의 구현·이름이 비슷한 ID·관행·예시 코드는 현재 서비스 계약을 확정하는 근거가 아니다.
- 미확정 계약을 임의 endpoint·DTO·ID 매핑·하드코딩·fallback·mock·fixture로 채워 구현을 진행하지 않는다. mock이 필요해도 사용자가 확정한 계약과 허용 범위를 먼저 확인한다. 타입 검사·빌드·자체 테스트 통과는 서비스 정책이 맞다는 근거가 아니다.
- 컴포넌트·hook·util·API client·상태 구조 등의 재사용 후보와 실제 사용처를 먼저 조사한다. 기존 자산이 없거나 요구를 충족하지 못하거나 재사용 적합성을 확인할 수 없으면 그 항목도 모두 사용자에게 질문한다. 부족한 기능과 기존 자산 확장·공용화·신규 작성 대안의 영향을 보고하고 방식을 확인받기 전에는 로컬 구현·복사·중복 작성·새 추상화를 임의로 선택하지 않는다.
- API 연결 시 현재 프로젝트의 `src/shared/api/common/`에 있는 공통 응답 DTO·schema와 실제 사용처를 먼저 확인하고, 서버 응답 계약이 일치하면 반드시 import하여 재사용한다. 동일한 envelope·pagination 구조를 도메인마다 중복 정의하지 않는다. 공통 envelope는 기존 `ApiClient`·mapper 경계에서 처리하고, API 호출의 응답 제네릭에는 내부 payload 타입을 전달한다.
- 질문은 확인한 근거, 필요한 항목과 이유, 누락된 결정, 선택지·영향을 구분해 제시한다. 발견한 필수 질문을 빠짐없이 모아 묻고 답변하지 않은 항목은 미확정으로 유지한다. 구현 도중 새 공백을 발견해도 동일하게 질문하고 해당 결정을 전제로 하는 구현을 보류한다. 상세 절차와 예시는 `task-role-routing`의 요청 명확성 게이트를 따른다.
- 사용자가 이미 구체적으로 확정한 같은 결정은 다시 묻지 않는다. 일반적인 `진행`·`Proceed`나 이전 계획 승인은 아직 보고·질문하지 않은 서비스 정책·데이터 계약·재사용 방식의 선택을 대신하지 않는다. 답변 없이 시간이 지났다는 이유로 권장안을 채택하지 않는다.

### 사용자 요청 명확성 게이트

- 모든 새 요청을 받았을 때와 다음 작업 또는 단계로 전환하기 전에, 현재 결정에 필요한 육하원칙을 확인한다. 확인 대상은 누가(사용자·대상·역할·소유자), 언제(시점·기한·순서), 어디서(project·repository·worktree·환경·경로), 무엇을(목표·결과물·변경 대상), 어떻게(방법·제약·검증·완료 기준), 왜(목적·우선순위·판단 기준)다.
- 여섯 항목을 형식적으로 모두 요구하지는 않는다. 다만 현재 단계의 결과, 범위, 대상, 권한, 순서, 외부 영향 또는 완료 기준을 달라지게 하는 정보가 누락·모호·상충하여 host가 임의로 선택해야 한다면 명확한 요청으로 간주하지 않는다.
- 요청이 명확하지 않으면 예외 없이 누락된 결정과 그 영향을 설명하고, 필요한 최소한의 중립 질문을 사용자에게 한 뒤 답변을 기다린다. 선택지가 있으면 차이와 권장안을 함께 제시할 수 있지만 사용자가 고르기 전에 특정 선택을 확정하지 않는다.
- 사용자 답변으로 모호성이 해소될 때까지 `can_proceed: false`로 처리한다. 질문을 구체화하는 데 필요한 요청·handoff·저장소 상태의 읽기 전용 확인 외에는 역할 확정, 계획 승인 요청, branch proposal, 파일 변경, 상태 변경·외부 영향 명령, 검증, 병합, 배포 또는 다음 파이프라인 단계로 진행하지 않는다.
- 현재 요청, 사용자가 명시적으로 승인한 직전 계약, 적용 가능한 최신 handoff와 확인된 저장소 사실이 관련 육하원칙을 이미 충족하면 같은 내용을 다시 묻지 않는다. host 관행, 기본값, 오래된 handoff 또는 추측을 사용자 의도나 승인으로 대체하지 않는다.

1. **역할 제안**: inject role이 없으면 사용자 요청과 적용 가능한 최신 `handoff.md`를 읽고 오케스트레이션·기획, Logic, UI, 통합 구현, 리뷰·평가·문서화 중 필요한 역할을 근거와 함께 제안한다. inject role이 있으면 요청이 해당 경계 안인지 확인한다.
2. **역할 확인**: inject role이 없으면 제안 역할, 예상 수정 범위와 필요한 스킬을 사용자에게 알리고 확인받는다. Git 통합 담당자나 파일·브랜치 독점 권한을 지정하지 않는다. 사용자가 같은 프롬프트에서 역할과 진행을 이미 명시했다면 그 지시를 확인으로 사용할 수 있다. inject role이 있으면 해당 role 경계를 확인하고 이 단계를 반복하지 않는다.
3. **Git 상태 확인**: 현재 branch·HEAD·worktree와 미커밋 변경을 확인한다. 모든 세션은 프로젝트의 모든 branch/worktree에 접근할 수 있다. 새 브랜치는 필요할 때 선택하며 생성 자체는 Git 변경 승인을 받는다.
4. **탐색**: 대상 코드와 인접 구현을 읽고, UI가 관련되면 `src/shared/ui/`를 먼저 조사하며 필요한 스킬만 불러온다.
5. **계획·구현 승인**: 예상 변경, 역할별 책임, 검증 방법, 예상 diff와 대안을 보고한다. 명시적인 `진행`, `진행해줘`, `전부 승인`, `모두 승인`, `Proceed` 또는 문서화된 동등한 승인 전에는 저장소를 변경하지 않는다. 공통 guard는 사용자 prompt의 승인을 assignment와 작업 범위별로 기록하고, 관련 `SKILL.md`와 역할별 재사용 자산·인접 구현을 실제로 확인하기 전 source mutation을 차단한다. 이 승인은 Codex의 정확한 shell 명령 1회 승인을 대신하지 않는다.
6. **Git 변경 승인**: 실행할 작업 위치·명령·대상과 영향을 제시하고 사용자 승인을 받는다. stage와 commit 같은 작업 단위는 한 번에 승인받을 수 있다. V3 계약과 proposal SHA 승인은 사용하지 않는다.
7. **구현**: 승인된 작업 범위와 역할에 맞게 한 번에 한 논리 구간씩 수정한다. branch에 scope를 고정하지 않는다.
8. **검토**: Watcher는 현재 변경의 통과 여부를 판정하고 Evaluator는 장기 개선 사항을 별도로 기록한다.
9. **문서화**: 작업 책임에 맞는 필수 산출물 또는 handoff를 작성한다. 기존 작업의 commit·merge만 수행하는 요청은 아래 산출물 예외를 적용한다.
10. **병합 승인과 정리**: 검증 결과, source·target, merge 방식과 정리 범위를 보고하고 별도 승인 후 merge·사후 검증·안전한 로컬 정리를 수행한다.

역할 확인은 구현 승인과 합칠 수 있다. 소스 구현 승인은 Git 변경 승인을 대신하지 않는다. 승인된 동일 Git 작업 단위는 다시 묻지 않으며 명령·위치·대상·변경 내용이 달라지면 다시 확인한다.

읽기 전용 조사에는 새 브랜치나 승인이 필요하지 않다. Git 운영의 단일 기준은 `git-branch-strategy`다.

Todo는 한국어로 작성하고 작업 위치, 수행 방법, 목적과 기대 결과를 포함한다. 세부 규칙은 `.agent-policy/common/skills/policy/documentation/SKILL.md`를 따른다.

## 3. 역할 계약

역할별 상세 책임은 `.agent-policy/common/skills/policy/task-role-routing/`의 공통 문서에서만 정의한다.

- 오케스트레이션·기획: `references/orchestration.md`
- Logic: `references/logic.md`
- UI: `references/ui.md`
- 통합 구현: Logic과 UI 문서를 함께 적용
- Planner·Publisher·Implementer/Generator·Refactorer·Watcher·Evaluator·Harness: `references/pipeline-roles.md`
- handoff·세션 기록·동시 작업: `references/handoff-and-ownership.md`

호스트 native agent 파일은 이 계약을 참조하며 역할 책임을 별도로 복제하지 않는다. 한 호스트가 여러 역할을 맡을 수 있고, 여러 호스트가 역할을 나눌 수도 있다. 역할 이름만으로 파일 수정 권한이 생기지 않으며 사용자 승인과 작업 범위를 지키고 기존 변경을 보호해야 한다.

## 4. 세션 산출물과 인계

### 정본 위치

세션 산출물 정본은 실행 호스트별로 분리한다.

- Codex: `.codex/logs/sessions/{YYYY-MM-DD-task-slug}/`
- Claude Code: `.claude/logs/sessions/{YYYY-MM-DD-task-slug}/`
- OpenCode: `.opencode/logs/sessions/{YYYY-MM-DD-task-slug}/`

### 산출물 책임

기존 변경의 commit·merge만 요청받은 경우, 새 세션을 포함해 `plan.md`, `final-summary.md`, `handoff.md`와 선택 로그를 새로 작성하지 않는다. 필요한 Git 상태 확인·검토·검증·승인·정리와 대화로 결과 보고만 수행한다. 예외는 현재 요청에 적용하며 세션 모드나 branch 범위로 고정하지 않는다. 같은 작업에서 구현·문서·설정을 직접 변경했다면 기존 작업 산출물에 commit·merge 결과를 함께 기록한다. 상세 범위와 예시는 `.agent-policy/common/skills/policy/documentation/SKILL.md`를 따른다.

그 외 작업에서 `owner`는 `plan.md`와 `final-summary.md`에 작업 범위, 결정, 실제 변경, 검증 결과와 미완료 항목을 기록한다. `contributor` 또는 중단·인계 시에는 `handoff.md`를 작성한다. 탐색·구현·리뷰·평가·portfolio·grill-me 기록은 작업 규모나 사용자 요청에 따라 선택한다. 한 작업의 기록을 역할별로 중복 작성하지 않는다.

문서 누락으로 Git 변경, 다른 작업 시작 또는 대화 종료를 차단하지 않는다. 정의되지 않은 보조 문서는 현재 세션의 `unknown/`에 둔다. 다른 host의 설정·로그 및 다른 세션의 산출물은 읽기 전용이다. 이미 커밋된 산출물을 승인된 병합으로 그대로 전달할 수 있으나 내용을 대신 작성하거나 고치지 않는다.

### 세션과 작업 위치

- assignment는 host·role·native session과 자기 산출물 경로를 식별한다. branch·worktree의 독점 권한이 아니다.
- 프로젝트의 기본 checkout, 기존 branch, 부모·자식·형제 branch와 모든 연결 worktree에서 같은 세션으로 작업할 수 있다. 기준 branch도 동일하게 사용자 Git 승인 규칙을 따른다.
- 명령 실행 경계는 launcher가 지정한 세션 프로젝트다. `user-ui` 세션에서 `admin-ui`를 대상으로 하는 명령과 그 반대는 조회를 포함해 실행하지 않는다. 다른 프로젝트 작업은 해당 프로젝트의 별도 세션에서 수행한다.
- 실제 `workdir`, `cd`, `git -C`, Git 저장소 옵션과 패키지 명령의 실행 경로를 확인한다. 연결 worktree는 경로의 상하 관계가 아니라 같은 Git common directory인지로 판정한다. 프로젝트 밖 대상은 Git 승인 전에 차단하며 사용자 변경 승인으로 이 경계를 확장하지 않는다.
- V1/V2/V3 metadata, git-integrator, Git claim, ACTIVE/CLOSED/PRESERVED와 완료 예약은 새 세션의 권한 판정에 사용하지 않는다. 기존 기록은 이력으로 보존한다.
- `--worktree`와 `--branch`는 시작 위치를 확인하는 선택값이고 `--task`는 작업 설명이다. branch 생성·CLOSED·소유권 인계 없이 기존 branch에서 새 세션을 시작할 수 있다.
- 실행 위치는 도구의 `workdir` 또는 `git -C`로 명시한다. host sandbox의 파일 쓰기 권한은 별개이며 필요한 경로만 승인받는다.
- 자기 산출물의 논리적 세션 경로는 worktree를 옮겨도 유지한다. 다른 host·세션의 로그를 직접 수정하거나 자기 commit에 임의로 포함하지 않는다.
- 소스와 산출물 파일 변경은 실제 대상이 드러나는 Edit/Write/apply_patch 도구를 사용한다. `.git` 내부 파일을 직접 편집하지 않고 사용자 승인 후 Git 명령으로 관리한다.
- Git 조회에는 구현 gate를 적용하지 않는다. Git 변경은 사용자 승인과 보호 실행기를 사용한다. 완료 통합에는 세션과 독립된 직접 부모 관계·미처리 자식 검사·형제 검토를 적용하며 구현 role·독점 소유권은 요구하지 않는다.

### handoff

commit·merge만 수행하는 요청에는 위 산출물 예외를 적용한다. 새 세션 시작·종료 자체가 handoff 작성 사유는 아니다.

작업자·호스트·세션·역할 담당자가 바뀌거나 정책 배포로 재시작할 때 현재 호스트 adapter의 `handoff.template.md`가 있으면 사용하고, 없으면 공통 handoff 필드로 같은 구조를 작성한다. 목표와 상태 외에 다음 항목을 포함한다.

- `requested_roles`, `confirmed_roles`, `completed_roles`, `next_role`
- 역할 판단 근거와 사용자 확인
- 보내는 작업의 실제 project·branch·HEAD·worktree 절대 경로와 인계 기준 시점
- **인계 대상 작업 위치**: 작업 공간별 식별 이름, 수행할 기능·하위 작업, 사용할 역할, project·저장소, 목적지 branch·worktree 절대 경로·실행 디렉터리, 확인한 HEAD 또는 생성 기준 commit, 직접 부모 branch, 기존 공간인지 생성 예정인지
- **역할별 상세 작업**: 사용할 작업 공간, 완료한 내용과 남은 목표, 수정할 파일·컴포넌트·hook·API·상태, 구체적인 변경 내용, 재사용 자산, props/callback·DTO 등 연결 계약, 선행 조건·작업 순서, 완료 기준·검증 명령과 다음 인계 대상
- commit 내역과 staged·unstaged·untracked 변경을 구분한 경로·변경 요약, 보존할 기존 변경, 역할 사이에 겹치는 파일·계약과 조율 방법
- 작업 공간을 공유하거나 분리하는 이유, 공유 시 수정·Git 실행 순서, 분리 시 부모·자식 관계와 통합 대상·순서, 승인된 Git 작업과 아직 승인받지 않은 작업
- 실행한 명령과 결과, 실행하지 않은 검증
- 차단 요인, 다음 조치와 필요한 스킬·정책

UI와 Logic이 같은 결과물을 순차로 연결하면 같은 branch·worktree를 작업 위치로 명시한다. 역할이나 세션이 다르다는 이유만으로 공간을 나누지 않는다. 실제 병렬 수정이나 별도 변경 이력·검증이 필요하면 작업별 branch·linked worktree를 명시한다. 공유 공간에서는 소스 수정과 Git 변경을 순차로 수행하고 전환 시 기존 변경을 재확인한다. Git 실행 lock이 편집까지 보호한다고 가정하지 않는다. 상세 작성법과 공유·분리 예시는 `.agent-policy/common/skills/policy/task-role-routing/references/handoff-and-ownership.md`를 따른다.

목적지·역할별 작업·연결 계약이 미확정이면 확인된 사실, 제안, 미정 항목을 구분하고 필요한 사용자 결정을 질문한다. 존재하지 않는 branch·worktree나 미승인 작업을 확정된 것으로 적지 않는다. 이미 승인되고 실제 상태로 확인되는 결정은 다시 묻지 않는다.

handoff의 작업 공간·파일 목록은 인계받을 작업의 실행 계획이며 세션의 작업 범위·브랜치 접근 권한이나 독점 소유권을 고정하지 않는다. `next_role`은 다음 역할의 제안이며 권한 부여가 아니다. 인계받는 작업자는 현재 사용자 요청과 실제 파일·Git 상태를 함께 읽고 목적지·HEAD·미커밋 변경의 차이를 확인한 뒤 작업한다. inject role이 없으면 역할을 다시 제안·확인하고, inject role과 `next_role`이 다르면 현재 역할을 확장하지 않고 올바른 role로 새 세션을 시작한다. 각 작성자는 자기 세션의 handoff만 갱신하며 다른 세션의 handoff는 읽기 전용으로 참조한다.

### 중앙 로그 미러링

- 활성 세션의 소비자 산출물이 원본이고 중앙 정책 저장소의 프로젝트·호스트별 로그는 추가·변경만 반영하는 Git 사본이다.
- 중앙 사본은 자동 삭제하거나 Git add·commit하지 않는다.
- 자동 수집 실패 시 경로와 오류를 보고하고 다음 종료 시점에 재시도한다. 필요하면 중앙 저장소에서 `bin/agent-policy collect-logs --project {{PROJECT_ID}} --channel all`을 실행한다.

`portfolio-log.md`는 사용자 요구, 문제 근거, 검토한 대안과 선택 이유, 실제 구현, 기술의 구체적 목적, 검증 결과와 후속 피드백을 기록한다. 대화에 없는 성과를 추정하지 않고 수치는 실행·측정 근거가 있을 때만 사용한다.

## 5. 병렬·순차 협업

- 같은 worktree의 Git 변경은 보호 실행기가 실제 명령 실행 구간에만 lock을 잡아 순차 처리한다. 승인 후에도 실행 직전에 관련 상태를 다시 확인한다. native Git lock을 임의로 삭제하지 않으며 세션 전체를 독점하는 소유권은 만들지 않는다.
- 사용자 요청·승인한 작업을 수행하며 다른 작업자의 변경을 되돌리거나 덮어쓰지 않는다. 계획의 파일 목록은 예상 diff이며 세션의 독점 권한으로 사용하지 않는다.
- 같은 파일을 수정해야 하면 기존 변경과 영향을 비교하고 필요한 보완을 보고한다. 파일 소유자를 지정하거나 인계를 의무화하지 않으며 이미 승인한 작업을 반복 승인받지 않는다.
- UI와 Logic을 나누면 props/callback, DTO, hook 또는 상태 계약과 인계 순서를 먼저 합의한다.
- 역할별 작업 위치와 구체적인 할 일은 handoff에 기록한다. 공유 branch·worktree에서 순차 작업할 수 있으며 역할·세션 수만큼 작업 공간을 만들지는 않는다. 같은 공간의 소스 수정도 순서를 조율하고 다른 작업자가 사용하는 branch를 임의로 전환하지 않는다.
- 별도 역할의 완료물을 연결할 때는 최신 파일과 handoff를 다시 읽고 사용자에게 통합 역할과 범위를 확인받는다.
- 병렬 수정에는 별도 linked worktree를 사용한다. 완료는 자식에서 직접 부모로 수행한다. 미처리 자식이 있으면 부모 완료를 차단하되 형제의 진행 자체는 차단하지 않는다. 형제의 현재·삭제 이력과 하위·미커밋 변경을 비교하고 위험·검증·미확인을 한 승인 보고에 담는다. 다른 기능 계열 이동은 한 번 안내하며 접근 제한이나 새 세션 의무로 만들지 않는다.

## 6. 관리 정책과 호스트 adapter

- 관리된 `AGENTS.md`, 호스트 지침, 하네스·스킬·훅은 소비자 프로젝트에서 직접 수정하지 않는다.
- 정책 변경이 필요하면 중앙 원본의 대상과 이유를 사용자에게 보고하고 중앙 저장소에서 수정한다.
- 소비자 저장소의 정책·프롬프트·훅 사본을 실행 원본으로 사용하지 않는다. 컴파일된 `__pycache__/*.pyc`를 포함해 host별 세션 로그와 허용된 개인 설정 외의 사본이 발견되면 제거하기 전까지 새 세션을 시작하지 않는다.
- 중앙 정책 변경을 적용하려면 현재 작업을 handoff한 뒤 중앙 launcher로 새 inject 세션을 시작한다. 기존 세션 resume은 시작 시 바인딩된 이전 bundle을 계속 사용하므로 최신 정책 적용으로 간주하지 않는다.
- Claude Code, Codex, OpenCode 고유 규칙은 system prompt에 바인딩된 중앙 snapshot과 host bundle에서 확인한다. 호스트 문서가 공통 역할을 재정의하거나 고정 배정할 수 없다.

## 7. 명령어

- 개발: `{{DEV_COMMAND}}`
- 빌드/타입 검증: `{{BUILD_COMMAND}}`
- 린트: `{{LINT_COMMAND}}`
- 테스트: `{{TEST_COMMAND}}`
- 프리뷰: `{{PREVIEW_COMMAND}}`

Git의 생성·수정·삭제·원격 반영은 사용자에게 대상과 영향을 설명하고 승인받는다. stage+commit 같은 명시적인 작업 묶음은 한 번에 승인한다. raw Git 변경은 현재 bundle의 git_operations.py 보호 실행기로 연결하며, 직접 ref 갱신·squash·rebase·cherry-pick을 완료 순서의 우회 경로로 쓰지 않는다. 조회와 일반 lint·test·build는 별도 승인 없이 수행한다. 완료 승인은 명시한 로컬 branch·linked worktree의 검증 후 정리를 포함할 수 있다. 실패 시 병합을 되돌리지 않고 정리만 보류한다. 원격 삭제·기본 worktree·현재 실행 위치는 자동 정리 대상이 아니다. CLOSED를 요구하지 않는다.

하네스 변경은 각 호스트 훅 단위 테스트로 검증한다. 대상 프로젝트에 test script가 있으면 함께 실행한다.

## 8. 테스트·리뷰 제한과 코드 양식

- 변경된 동작을 확인하는 최소 테스트를 기존 도구와 배치 규칙으로 작성한다.
- 사용자 보고 또는 실행 로그로 확인된 정책·훅·세션 실행 결함을 수정할 때는 그 실패 상황을 재현하는 자동 회귀 테스트를 함께 작성한다. 수정 전 구현에서 실패하고 수정 후 구현에서 통과하는지 확인하며, 회귀 테스트가 없는 정책 변경은 완료로 처리하지 않는다.
- 공통 정책이나 host adapter의 동작을 변경하면 영향받는 Codex·Claude Code·OpenCode 전체를 같은 계약으로 검증한다. 명령 문자열이나 생성 파일의 존재만 확인하지 않고 실제로 적용되는 프롬프트·설정·훅 출처를 검증한다. primary checkout과 별도 worktree의 동작이 달라질 수 있으면 두 위치를 모두 포함한다.
- 기존 회귀 테스트를 삭제하거나 검증을 약화해 통과시켜서는 안 된다. 의도적인 계약 변경으로 기대값을 바꾸는 경우에는 변경 이유와 대체 검증을 테스트 또는 작업 기록에 남긴다.
- 훅 차단을 수정할 때는 정상 허용 사례와 함께 소비자 legacy 훅 혼입, host별 산출물 경로 충돌, 서로 다른 worktree·Git 대상 변경, 종료 훅의 반복 호출을 실패 사례로 검증한다. 동일 원인의 훅 차단을 무한히 재시도하지 않는다. 같은 차단 원인이 반복되면 재실행 없이 한 번만 보고하고 사용자 입력 또는 외부 상태 변경을 기다린다.
- 테스트만을 위한 별도 프레임워크나 과도한 설정·헬퍼를 추가하지 않는다.
- 이미지 캡처, GIF 녹화, 화면 비교, 브라우저 자동화 캡처와 시각 QA는 사용자가 요청하지 않는 한 수행하지 않는다.
- Watcher 외 별도 리뷰 자동화를 임의 실행하지 않는다.
- 코드 수정 전 같은 디렉터리와 인접 구현을 확인하고 import 순서, 따옴표, 세미콜론, 들여쓰기와 JSX 양식을 따른다.
- 관련 없는 코드의 포맷·재배치·정리는 하지 않는다.

## 9. 이벤트·상태 계약

- SessionStart·branch-context는 실제 Git 상태와 소스 구현 준비를 조회한다. branch 생성이나 계약·소유권 인계를 지시하지 않는다.
- UserPromptSubmit은 구현 승인·철회와 대기 중인 Git 작업 승인을 구분한다. Codex·OpenCode의 `명령 실행 승인`만 현재 Git 작업을 승인한다. `진행`·`Proceed`는 구현 승인이다. Claude는 보호 실행의 native 권한 요청을 사용한다. 승인 SHA를 사용자에게 요구하지 않는다.
- 명령 승인 요청·응답과 승인 후 실행 예약은 경과 시간만으로 만료되지 않는다. 승인은 보고한 동일 작업의 1회 실행 범위이며 실제 실행 전 대상·변경 내용과 현재 실행 주체를 다시 확인한다.
- PreTool은 관리 정책·host 설정·세션 산출물 보호, 실제 Git 대상과 변경 승인을 확인한다. 소스 수정에만 역할·구현 승인·성공한 탐색 근거를 적용한다.
- PostTool은 확인된 성공만 탐색 근거로 기록하고, 산출물 쓰기의 성공·실패를 반영한다. 미확인 산출물 이벤트가 branch 접근이나 Git 독점 권한을 만들지 않는다.
- Stop/idle은 로그를 수집한다. 문서 누락으로 종료를 반복 차단하거나 자동 merge·close하지 않는다.
- 기존 inject 세션은 원래 bundle을 유지한다. 새 정책은 handoff를 읽고 중앙 launcher로 새 assignment를 시작해 적용한다. Git 소유권 인계는 필요하지 않으며 `--resume-assignment`는 원래 정책 재개다.
- hook이 관찰하지 않는 shell 후속 입력과 미등록 도구까지 보호한다고 가정하지 않는다. host sandbox와 사용자 실행 권한은 별개다.

## 10. 필수 승인 문구

역할과 구현 계획 보고는 다음 문구로 끝낸다.

`이 역할과 계획대로 진행할까요, 아니면 조정할 부분이 있나요?`

사용자가 명시적으로 승인하기 전에는 애플리케이션 소스, 정책 또는 패키지 파일을 수정하지 않는다. 승인 문장이 테스트 순서처럼 계획을 제한하는 조건을 함께 담아도 조건을 지키며 진행할 수 있다. 부정, 거부, 취소와 보류는 항상 승인보다 우선한다. Git 작업 단위의 승인은 일반 구현 승인과 구분하며 사용자에게 제시한 실제 대상·명령·영향을 지킨다.
