# 리뷰 점검표

목표 충족 범위, 승인 근거, 불러온 스킬, 타입 안전성, 검증 및 요청 데이터 완전성, 중복 로직, 렌더링 비용, 접근성, 빌드 및 정적 분석 결과, 문서화를 확인한다. UI 구현이 포함될 때 `src/shared/ui/` 재사용과 디자인 정책을 필수 항목으로 적용한다. 파일 수준의 근거와 함께 PASS 또는 FAIL을 보고한다.

UI 구현은 [UI 자산 선정과 라이브러리 정책](../ui-library/SKILL.md)에 따라 계획 단계의 `unknown/ui-asset-plan.md`가 모든 구현 항목을 다루는지, 실제 자산·계약과 일치하는지 확인한다. 작업 범위의 외부 UI 라이브러리에 사용 스킬 또는 세션 초안이 있고 목적·구현 계약·사용법과 검증 근거가 실제 구현에 맞는지 확인한다. 중앙 등록 전인 초안을 등록 완료로 보고했거나 필수 문서·항목이 누락되면 해당 구현 검토를 FAIL로 보고한다. 리뷰만 맡은 세션은 대상 문서를 읽고 발견 사항을 기록하며 다른 세션의 문서를 대신 작성하지 않는다.

UI·API 연결은 [controller 계약](../../recipe/api-authoring/references/ui-controller.md)에 따라 UI 없는 controller와 양방향 매핑, 선행 구현·계약 제공자·적용 방향을 확인한다. UI 선행에서 UI 항목과 controller·DTO가 불일치한 경우 사용자 질문·답변과 실제 반영 근거가 있어야 한다. 근거 없이 UI 변경·필드 누락·임의 기본값·강제 변환으로 차이를 숨겼거나 controller에 렌더링 구현을 넣었다면 해당 연결을 FAIL로 보고한다.

새 서비스 개념·API·요청/응답 필드·ID 매핑·기본값·업무 흐름에는 현재 프로젝트의 확인된 계약 또는 해당 결정을 확정한 사용자 답변이 있는지 확인한다. 재사용 자산이 없거나 부족했던 항목에도 확장·공용화·신규 작성 방식의 사용자 확인 근거가 있어야 한다. 근거 없이 채운 계약과 재사용 결정을 발견하면 해당 변경을 FAIL로 보고하고 질문으로 되돌린다. 자체 mock·fixture·타입 검사·빌드·테스트 통과를 서비스 계약의 근거로 인정하지 않는다.
