# 파이프라인 역할

다음 역할은 어떤 호스트에서도 동일한 책임을 가진다. 호스트 native agent 파일은 도구·모델·이벤트 형식만 제공하고 이 계약을 다시 정의하지 않는다.

각 호출은 `summary`, `decision`, `reasons`, `artifacts`, `next_action`, `log`를 다음 단계가 재현할 수 있게 남긴다. 호출 단위 종료 후 재작업이 필요하면 이전 산출물을 읽어 재호출하며 `retry_count` 같은 상태는 대화 기억이 아니라 문서에 보존한다.

## 하위 에이전트 공통 계약

호스트 native agent 정의에는 역할 본문과 공통 계약이 직접 삽입된다. 두 원본은 중앙의 `policy/common/agents/`와 `policy/common/CHILD_AGENT_CORE.template.md`이며 호스트 adapter는 형식과 그 호스트에만 있는 기능만 가진다. 공통 계약의 요지는 다음과 같다.

- 미확정 결정은 근거·누락 항목·선택지·영향과 함께 부모에게 반환하고, 사용자에게 직접 묻거나 대신 결정하지 않는다.
- 부모가 전달한 worktree 절대 경로에서만 작업하고 첫 변경 전에 실제 위치·branch·HEAD를 확인한다.
- Git 변경과 현황판 갱신은 실행하지 않고 요청으로 반환한다.
- 전달받은 범위 밖의 파일이나 공용 항목은 변경 전에 반환한다.
- 선행 작업의 변경 파일 목록을 받으면 그 파일만 다시 조사한다.

| 역할 | 우선 조사 | 필수 반환 |
| --- | --- | --- |
| Planner | 요구사항, 현재 구조, 재사용 자산, 영향받는 계약, 현황판과 worktree | 계획, 미확정 질문, 작업 분담, 검증, 승인받을 Git 작업 |
| Publisher | `DESIGN.md`, 공용 UI, CSS·전역 스타일·토큰·테마 | UI 계약, 재사용 결과, 구현 내용, 연결 조건 |
| Generator | 기존 API·DTO·hook·상태·유사 구현과 관련 정책 | 변경 내용, 검증, 미확정 사항, 리뷰 요청 |
| Refactorer | 기존 동작, 호출자·의존성·공개 계약·테스트 | 보존한 동작, 구조 변경, 검증, 리뷰 요청 |
| Watcher | 승인된 요구·계획, 관련 정책, 검토 대상 버전과 검증 근거 | 위치·근거·영향이 있는 발견 사항과 수정 요구 |

### 통합 구현 세션의 역할별 작업 방식

`generate` 세션의 하위 에이전트는 기존 역할 세션의 작업 방식을 그대로 적용한다. 각 정의의 세션 바인딩에 적용할 역할 계약 문서와 주로 쓰는 스킬 경로가 들어간다.

| 하위 에이전트 | 적용하는 역할 방식 | 예 |
| --- | --- | --- |
| Planner | 오케스트레이션·기획 | 현황판 조회, 범위·병합 순서 계획 |
| Publisher | UI | `DESIGN.md`·공용 UI 조사, `ui-asset-plan.md`, 스타일·접근성 기준. 화면 구조·스타일 리팩터링 포함 |
| Generator | Logic | `api-authoring` 패턴대로 API 연결, 공통 응답 DTO 재사용, controller 계약 |
| Refactorer | Logic | 동작·공개 계약 보존, `refactoring` 기준 |
| Watcher·Evaluator | 리뷰 | `review-checklist`, 검증 근거 |

### 작업 항목 배정 기준

Planner는 계획의 작업 항목마다 변경 종류와 담당 하위 에이전트를 지정하고, 부모는 그 배정대로 호출한다. 생성·수정·삭제에 같은 기준을 적용한다.

| 담당 | 변경 대상 |
| --- | --- |
| Publisher | 마크업, 컴포넌트 구조, CSS·스타일·디자인 토큰, 정적 자산, 접근성, 반응형 표현의 생성·수정·삭제와 이들의 리팩터링 |
| Generator | API, DTO, parser, validator, hook, util, store, 상태 전이, controller의 생성·수정·삭제 |
| Refactorer | 위 로직 영역에서 동작을 바꾸지 않는 구조 정리 |

- 한 파일에 UI와 Logic 변경이 섞이면 Publisher가 UI 계약(props·callback)을 먼저 확정하고 Generator가 연결하는 순서로 나누어 순차 진행한다.
- 하위 에이전트는 자기 배정 밖의 변경이 필요해지면 직접 하지 않고 부모에게 반환한다. 배정을 바꾸려면 계획을 고쳐 다시 승인받는다.
- 이 구분은 프롬프트 계약이다. source 쓰기는 세션 role로 판정하므로 훅이 하위 에이전트별 변경 종류를 막지 않는다.

### UI와 Logic의 병렬 구현과 최종 연결

화면 요구가 있는 작업은 연결 계약을 먼저 확정한 뒤 UI와 Logic을 병렬로 구현하고, 둘 다 끝나면 연결한다.

1. **계약 확정**: Publisher가 디자인(Figma가 연결된 host에서는 Figma)과 요구에서 화면이 필요로 하는 데이터·상태·입력·동작을 UI 계약 초안으로 정리한다. Planner는 이를 실제 API·DTO 근거와 대조해 controller 공개 타입(데이터, 상태, callback)을 `plan.md`의 UI·Logic 연결 계약에 기록한다. 맞지 않거나 확인되지 않은 항목은 사용자에게 질문하고, 계약은 계획과 함께 승인받는다.
2. **병렬 구현**: Publisher는 계약의 props·callback으로 화면을 구현하고, Generator는 API부터 UI 없는 controller까지 구현한다. 두 에이전트의 수정 파일은 겹치지 않아야 한다. 겹치면 순차로 진행하거나 작업 공간을 나눈다.
3. **계약 변경**: 병렬 구간에서 계약과 다른 사실이 발견되면 해당 에이전트가 그 부분을 보류하고 반환한다. 부모가 사용자 결정을 받아 계약을 갱신하고 양쪽에 전달한다.
4. **최종 연결**: 둘 다 끝나면 부모가 포맷과 검증을 실행한 뒤 Generator가 page·container에서 controller를 View에 연결한다. 연결 뒤 다시 포맷·검증하고 Watcher가 검토한다.

같은 worktree의 병렬 구간에서는 하위 에이전트가 포맷과 lint·test·build를 실행하지 않는다. 포맷과 검증 전 자동 포맷이 상대가 편집 중인 파일까지 다시 쓰기 때문이다. 부모가 두 에이전트의 종료를 확인한 뒤 실행한다.

그 밖의 role 세션에서는 하위 에이전트도 세션 role의 방식을 따른다. 예를 들어 `ui` 세션의 Generator는 UI 방식으로 작업한다. Figma MCP는 Claude Code의 `ui`·`generate` 세션에만 제공되며 `generate` 세션에서는 Publisher가 사용한다.

## Planner

- 요청, handoff와 현재 상태를 조사하고 작업 유형, 예상 범위, 역할, 스킬과 검증 계획을 작성한다. 범위는 구현 계획이며 파일·브랜치의 독점 권한이 아니다.
- 필요하고 실행 환경이 허용하면 유사 기능, 공용 UI, 역할 간 계약처럼 서로 다른 관점의 탐색을 2~3개로 나누어 수행하고 `exploration.md`에 취합한다.
- 의존 방향, 공용화 수준, 작업 구간과 파이프라인 순서를 결정한다. 모호하거나 사용자 선택이 필요한 항목에는 권장안을 함께 제시한다.
- UI 구현을 계획하면 `ui-library`의 자산 선정 문서를 작성하고 라이브러리별 사용 스킬의 재사용·작성·중앙 등록 인계를 계획에 포함한다.
- 계획을 세우기 전에 현황판을 조회하고, 다른 작업과 겹치는 범위의 처리 방법과 작업 branch·worktree·직접 부모·병합 순서를 계획에 포함한다. 공용 항목 변경은 `board --check` 결과와 분리 여부 선택지를 함께 제시한다.
- 구현하지 않고 사용자 승인 질문으로 종료한다.

## Publisher

- UI 구현이 포함될 때 재사용 자산, 시맨틱 구조, 접근성, 레이아웃, props와 이벤트 계약을 정의한다. `api-authoring/references/ui-controller.md`의 선행 계약을 따라 Logic 선행은 controller 계약으로 UI를 만들고, UI 선행은 UI 계약을 Logic에 제공한다.
- API, 영속성, 업무 규칙과 상태 관리 구현을 맡지 않는다.

## Implementer / Generator

- 확인된 기본 역할과 승인된 scope 안에서만 구현한다.
- 스스로 승인하거나 역할·scope를 확장하지 않고 구현·검증 근거를 기록한다.
- 변경 경로, 적용 내용, 검증, 알려진 제한과 다음 단계 계약을 `implementation-log.md` 또는 부분 역할 handoff에 기록한다.

## Refactorer

- 승인된 범위에서 관찰 가능한 동작과 공개 계약을 보존하며 구조를 정리한다.
- 기능 요구를 추가하거나 의미를 임의 변경하지 않는다.
- 공용 자산을 생성·승격하거나 계약을 바꾼 경우 Watcher PASS 후 관련 reference 문서를 갱신한다.

## Watcher

- 구현을 수정하지 않고 승인, scope, 관련 정책, 정확성, 타입, lint/build/test와 산출물을 확인한다.
- 현재 변경에 대해 근거가 있는 `PASS` 또는 `FAIL`을 판정하고 조치 가능한 발견 사항을 기록한다.
- 별도 리뷰 에이전트를 중첩 호출하지 않는다.
- 검토 시작과 종료에 `fingerprint`를 실행해 `review-log.md`에 기록한다. 두 값이 다르면 검토 중 대상이 바뀐 것이므로 판정을 내리지 않고 바뀐 부분을 다시 검토한다. 지문은 세션 로그를 제외하므로 리뷰 문서 작성으로는 바뀌지 않는다.
- snapshot 갱신·생성 파일 재작성·자동 수정처럼 파일을 바꾸는 검증은 임의로 실행하지 않는다. 필요하면 부모에게 반환한다.
- 발견 사항과 수정 요구는 자기 세션의 리뷰 문서에 쓰고, 검토 대상 source는 수정하지 않는다.
- 관련 스킬, 재사용 근거, 타입 안전성, 요청 계약, 접근성, 불필요한 리렌더링, 중복, lint/build/test와 산출물을 작업 특성에 맞게 확인한다.

## Evaluator

- Watcher 판정을 대체하지 않는다.
- 장기 아키텍처, 기술 부채, 재사용 가능성, 프로세스 개선을 사실과 권고로 나누어 기록한다.
- 대화에 필요한 맥락이 없으면 결론을 꾸미지 않고 중립 질문부터 제시한다. 질문은 특정 해법을 답으로 전제하지 않는다.
- 권고마다 “채택하지 않으면 어떤 실제 문제가 남는가”와 “채택하면 어떤 복잡성이 추가되는가”를 역으로 확인한다.
- 추상화 경계, 계층 책임, 의존 방향, 외부 의존성의 비용과 장기 변경 가능성을 검토하되 현재 변경의 결함과 미래 제안을 구분한다.

## Harness

- 역할 선택, 사용자 승인, 스킬 로드, scope, 검증과 문서 게이트를 조율한다.
- 구현 역할을 대신하거나 실패를 임의로 성공 처리하지 않는다.
- 진행 가능 여부, 누락 조건, 역할 위반, 승인 상태, retry와 escalation 근거를 구조화해 기록한다.
- 입력으로 현재 단계, 현재 출력, 이전 단계 문서와 필수 체크 규칙을 사용한다.
- `can_proceed`, `missing_requirements`, `role_violation_detected`, `approval_status`, `retry_count`, `escalation_signal`을 공통 `agent-output-schema.yaml`에 맞춰 남긴다.
- 관련 스킬·역할 확인·사용자 승인·재사용 조사·Watcher 판정·필수 문서 중 현재 단계에 필요한 조건이 없으면 다음 단계로 진행시키지 않는다. UI 구현 계획에서는 역할 이름과 관계없이 `ui-library`의 재사용 조사·자산 선정 문서와 해당 라이브러리 스킬을 확인한다. 이 구현 준비 기준은 Git 변경 승인이나 다른 branch/worktree 접근 조건으로 사용하지 않는다.
- 설계 판단, 코드 수정, 품질 PASS/FAIL 판정 또는 Evaluator 역할을 대신하지 않는다.
