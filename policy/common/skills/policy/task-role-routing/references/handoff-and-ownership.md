# Handoff와 작업 기록

handoff는 작업 연속성을 위한 상태 기록이며 구현 승인이나 Git 변경 승인을 대신하지 않는다.

## 작성 시점과 내용

기존 변경의 commit·merge만 수행하는 요청은 새 세션이나 인계 시점에도 `documentation`의 산출물 예외를 적용한다. 별도 handoff를 만들거나 이전 세션의 누락 기록을 보충하지 않고 실제 Git 상태와 처리 결과를 대화로 보고한다.

작업자·host·role·세션이 바뀌거나 중단할 때 목표, 현재 상태, 완료·대기 작업, 결정, 실제 경로·branch·HEAD·worktree, dirty/staged 변경, 명령과 검증 결과, 다음 조치를 기록한다. 역할 필드는 `requested_roles`, `confirmed_roles`, `completed_roles`, `next_role`을 사용한다. 인계받는 세션은 최신 사용자 요청과 실제 Git 상태를 함께 확인한다. inject role이 있으면 같은 역할을 반복 확인하지 않는다.

## 인계 대상 위치와 역할별 작업

공통 `.agent-policy/common/templates/handoff.template.md`를 사용한다. “현재 A branch에서 작업했다”는 기록만으로 목적지를 대신하지 않는다. 다음 작업자가 **어떤 작업을 어느 공간에서 어떤 순서로 끝내야 하는지** 확인할 수 있어야 한다.

1. **보내는 현재 상태**: project·저장소 루트, 실제 branch·HEAD·worktree 절대 경로·실행 디렉터리와 확인 시점을 적는다. 완료한 commit과 경로별 변경을 요약하고 staged·unstaged·untracked 변경을 각각 기록한다. 미커밋 변경도 인계 내용에 포함하며 다른 작업자의 변경, 보존할 파일과 미완료 검증을 구분한다.
2. **인계 대상 작업 공간**: 공간마다 식별 이름을 붙이고 수행할 기능·하위 작업, 사용할 역할, project·저장소, 목적지 branch·worktree 절대 경로·실행 디렉터리, 확인한 HEAD 또는 생성 기준 branch·commit, 직접 부모를 적는다. 기존 공간은 확인 근거를 남기고 생성 예정 공간은 제안과 생성 승인 여부를 구분한다. 같은 공간을 쓸 UI·Logic은 동일한 공간 이름을 참조한다.
3. **역할별 작업 지시**: 역할마다 공간 이름, 완료한 내용, 남은 목표, 파일·컴포넌트·hook·API·상태별 구체적인 변경과 이유를 적는다. 재사용 자산과 확장 방법, props/callback·DTO·hook·상태 계약 및 근거, 선행 조건·수정 순서, 겹치는 파일과 조율 방법, 완료 기준·검증 명령·기대 결과, 다음 인계 역할과 목적지를 작성한다. “UI 마무리”, “Logic 연결”만 적지 않는다.
4. **공유·분리와 통합**: 공간 선택 이유, 공유 공간의 수정·Git 순서, 분리 공간의 부모·자식 관계와 통합 대상·순서를 적는다. 형제 검토에는 commit과 미커밋 변경, 이미 통합·삭제된 형제의 이력도 포함한다. 검사 결과와 아직 확인하지 않은 위험, 승인된 Git 작업과 미승인 작업을 구분한다.

목적지나 역할별 작업·서비스 계약이 미정이면 조사한 사실과 제안을 남기고 필요한 결정을 사용자에게 질문한다. 다른 공간에서 이어갈 작업의 미커밋 변경이 저절로 전달된다고 가정하지 않으며, 어떤 변경을 어떤 승인된 Git 작업으로 전달할지 명시한다. 기존 요청·승인과 실제 저장소 사실로 확인되는 항목은 다시 묻지 않는다.

인계받는 작업자는 문서의 목적지와 실제 repository·branch·HEAD·변경 상태를 비교한다. HEAD가 달라졌으면 추가된 commit과 미커밋 변경을 확인하여 계획에 미치는 영향을 판단한다. 문서의 HEAD로 되돌리거나 현재 변경을 덮어쓰지 않는다. 필요한 사용자 결정이 달라진 경우에만 갱신된 선택을 확인받는다.

이 정보는 작업의 실행 계획이다. 세션별 허용 branch·worktree·파일 목록이나 독점 소유권을 만들지 않는다. 다른 기능 계열로 이동할 때는 기존 정책대로 적절한 작업 위치와 선택적인 새 세션을 안내한다.

## 같은 공간을 쓰는 경우

UI와 Logic이 하나의 결과물을 순차로 연결하고 독립적인 수정·검증이 필요하지 않다면 같은 branch·worktree를 공유한다. 역할이나 세션이 다르다는 이유로 branch를 추가하지 않는다. 여러 세션에서 같은 공간을 읽을 수 있지만 소스 수정과 Git 변경은 작업 구간별로 순차 실행한다. 다음 작성자는 앞선 쓰기가 끝났는지와 실제 diff를 확인한다. Git 실행 lock은 편집 충돌을 막지 않으므로 다른 작업자가 쓰는 중에 branch를 전환하거나 변경을 되돌리지 않는다.

### 예시: UI 완료물을 같은 공간에서 Logic이 연결

아래 경로·이름·계약은 작성 형식을 보여주는 예시다. 실제 프로젝트에서 존재하거나 승인된 것으로 간주하지 않고 조사·확인한 값으로 바꾼다. 예시에서는 UI와 Logic의 계약이 이미 확인되었다고 가정한다.

- 작업 공간 `A-shared`: 같은 프로젝트의 기존 branch `A`, worktree `/workspace/worktrees/A`, 실행 디렉터리도 동일. 직접 부모는 `sy-main`, HEAD는 인계 시 조회한 전체 SHA를 기록한다. 두 역할 모두 이 공간을 사용한다.
- 인계 상태: UI가 작성한 commit은 SHA·요약·변경 파일을 기록하고, 남아 있는 staged·unstaged·untracked 파일은 각각 내용과 보존 방법을 기록한다. 실제 변경이 없으면 `없음`으로 쓴다.

| 역할 | 구체적인 작업 | 시작 조건·완료 기준 |
| --- | --- | --- |
| UI | `src/features/tasks/TaskPanel.tsx`에서 확인된 공용 목록·버튼을 재사용해 목록, 로딩, 오류, 빈 상태를 표시한다. 확정된 `items`, `isLoading`, `error`, `onRetry` props를 사용하고 API 요청은 수행하지 않는다. | props 계약 확인 후 수정한다. 각 상태 렌더링·재시도 callback·접근성을 기존 검증 명령으로 확인하고 결과와 남은 변경을 handoff에 적는다. |
| Logic | `src/features/tasks/useTask.ts`에서 프로젝트에 존재하는 API client·응답 DTO·상태 처리를 재사용하고 `TaskPanel.tsx`에 hook 결과와 재시도 동작을 연결한다. | UI의 쓰기가 끝나고 최신 diff·검증 결과를 확인한 뒤 시작한다. 요청 성공·실패·재시도 흐름과 화면 연결을 해당 프로젝트의 실제 테스트·빌드·린트 명령으로 검증한다. |

두 역할 모두 `TaskPanel.tsx`를 변경하므로 **UI 수정 종료 → Logic이 최신 props와 diff 확인 → Logic 연결 → 전체 검증** 순서로 진행한다. 실제 handoff에는 실행할 검증 명령과 기대 결과도 적는다. 같은 branch 안의 순차 인계이므로 역할 사이에 별도 merge는 필요하지 않다. 필요한 stage·commit은 대상 diff를 확인하고 사용자 승인 범위에서 실행한다. 각 역할은 자기 세션의 산출물에 기록하며 상대 세션의 handoff는 읽기 전용으로 참조한다.

## 공간을 나누는 경우

실제 병렬 수정, 서로 독립된 변경 이력 또는 별도 검증 환경이 필요하면 작업별 branch·linked worktree로 분리한다. 하나의 branch를 여러 linked worktree에 강제로 checkout하지 않는다. 분리 작업도 같은 공용 계약에 영향을 줄 수 있으므로 파일이 다르다는 이유로 검토를 생략하지 않는다.

### 예시: UI와 Logic을 병렬 구현한 뒤 A에 통합

다음 역시 예시이며 실제 경로·기준 SHA·생성 승인·검증 명령으로 구체화한다. 출발점 `A`의 확정된 props·DTO 계약 commit을 공통 기준으로 삼는다. commit되지 않은 계약 변경이 있으면 전달 방법부터 확인한다.

| 작업 공간 | 역할과 작업 | 목적지·분기 기준 |
| --- | --- | --- |
| `A-ui` | UI가 `TaskPanel.tsx`의 상태별 표시와 callback 계약을 구현·검증한다. 새 API나 임의 응답 데이터를 만들지 않는다. | branch `A-ui`, worktree `/workspace/worktrees/A-ui`, 직접 부모 `A`, 분기 기준은 확인된 계약 commit의 전체 SHA. |
| `A-logic` | Logic이 기존 client·DTO를 이용해 `useTask.ts`의 요청·상태·재시도 동작을 구현·검증한다. hook 반환형은 확인된 props 계약에 맞춘다. | branch `A-logic`, worktree `/workspace/worktrees/A-logic`, 직접 부모 `A`, 분기 기준은 같은 계약 commit의 전체 SHA. |
| `A-integration` | 확인된 통합 역할이 두 결과를 연결하고 요청부터 화면까지 전체 동작을 검증한다. | 기존 branch `A`, worktree `/workspace/worktrees/A`, 직접 부모 `sy-main`. |

실제 handoff에는 각 공간의 기존/생성 예정 여부, 실행 디렉터리, HEAD, 남은 상세 변경, 검증 명령·결과·완료 기준을 위 형식대로 채운다. 예상 순서는 **`A-ui → A`, `A-logic → A` → A에서 연결·전체 검증 → `A → sy-main`**으로 기록할 수 있다. 형제 둘 사이의 순서는 검토와 사용자 승인으로 정하며 자식에서 직접 부모로의 통합 순서는 지킨다. 자식에 더 하위 작업이 있으면 그 작업부터 처리한다. 부모 관계는 이름으로 추측하지 않고 등록된 관계로 확인한다. 예시의 `A`와 자식 이름은 Git ref 경로도 충돌하지 않게 정한다.

merge 전 두 형제의 commit과 staged·unstaged·untracked 변경을 비교하고, 공용 props·DTO·컴포넌트에 겹치는 내용이 있으면 파일과 변경 내용을 설명하여 승인받는다. 먼저 통합하고 정리된 형제의 이력도 다음 형제 검토에 포함한다. 통합·사후 검증을 마친 branch·worktree의 안전한 정리는 `git-branch-strategy`를 따른다.

## 산출물

`owner`는 `plan.md`와 `final-summary.md`를 작성한다. 부분 기여자 또는 중단·인계는 `handoff.md`로 남긴다. 세부 탐색·구현·리뷰·평가·portfolio·grill-me 문서는 필요에 따라 선택한다. 문서 누락으로 Git이나 다음 작업을 차단하지 않는다.

자기 세션의 논리적 산출물 경로만 수정한다. 다른 host의 설정·로그와 다른 세션 기록은 읽기 전용이다. 이미 커밋된 기록을 branch 병합으로 전달할 수 있다. 정의되지 않은 보조 기록은 자기 세션의 `unknown/`에 둔다.

## Git과 동시 작업

모든 세션은 프로젝트의 모든 branch/worktree에서 사용자 승인 후 Git 변경을 실행할 수 있다. contributor·host·assignment로 실행자를 제한하지 않는다. 완료 통합은 미처리 하위 작업이 없는 자식에서 직접 부모로 수행하며 형제 검토와 승인을 받는다. 세션 독점 Git claim과 CLOSED 해제 절차는 없다. 보호 실행기의 짧은 Git lock을 사용하며 병렬 구현에는 별도 linked worktree를 사용한다. 다른 작업의 변경을 덮어쓰거나 임의로 commit하지 않는다.

새 정책 적용 시 현재 세션을 handoff하고 새 inject assignment를 시작한다. Git 소유권 이전 명령은 필요하지 않으며, 과거 assignment를 resume하면 원래 bundle을 사용한다.
