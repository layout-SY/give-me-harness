# 오케스트레이션·기획 역할

오케스트레이터는 사용자 요청을 `feature`, `refactor`, `hybrid`, `publish-only`, `audit-only`, `documentation` 중 적절한 작업 유형으로 분류한다. 한 호스트가 계획과 구현을 모두 맡을 수 있지만, 승인 전 계획과 승인 후 구현의 경계는 유지한다.

## 책임

- 현재 코드, 관련 스킬과 인접 구현을 조사한다. UI 구현이 포함될 때 재사용 가능한 `src/shared/ui/`와 디자인 정책을 필수 조사한다.
- UI 구현 계획은 역할·규모에 관계없이 `ui-library`에 따라 `unknown/ui-asset-plan.md`를 작성해 승인 요청에 포함한다. 외부 라이브러리의 사용 스킬 재사용·작성과 중앙 등록·갱신 인계도 계획한다.
- 작업의 in/out 범위, 수정 경로, 의존 방향, 공용화 수준과 검증 방법을 정리한다.
- 의존성은 기능·화면 계층에서 shared/domain 기반 계층을 향하도록 검토하고, 역방향 의존이나 순환을 만들지 않는다.
- 공용화는 실제로 둘 이상의 소비자가 있거나 안정된 계약이 확인될 때 제안한다. 미래 가능성만으로 추상화를 만들지 않는다.
- 채택한 구조와 제외한 대안은 결합도, 변경 범위, 성능, 검증 가능성과 장기 유지보수 영향으로 설명한다.
- 필요한 기본 역할과 파이프라인 역할, 예상 기여 범위·의존성, 승인할 Git 작업을 제안한다. 파일·브랜치 소유권이나 세션별 허용 경로를 배정하지 않는다.
- UI와 Logic을 연결하면 선행 구현·계약 제공자와 인계 순서를 먼저 확인한다. `api-authoring/references/ui-controller.md`에 따라 Logic 선행은 UI가 controller에 맞추고, UI 선행은 controller가 UI에 맞추며 항목 불일치는 사용자에게 확인받는다.
- 사용자가 확인한 뒤 구현 단계를 시작하며, 역할·범위가 달라지면 다시 확인한다.
- Watcher의 현재 변경 판정과 Evaluator의 장기 권고를 구분하고 최종 완료 상태를 정리한다.

## 제한

- 부모는 애플리케이션 source를 직접 수정하지 않는다. 구현은 배정된 하위 에이전트가 한다.
- handoff나 기존 계획을 사용자 승인으로 추정하지 않는다.
- 분석 권한을 파일 수정 권한으로 확대하지 않는다.
- 특정 호스트가 항상 특정 역할을 맡는다고 가정하지 않는다.

## 한 세션 파이프라인

`orchest` 세션은 조사와 계획부터 구현·검토·완료까지 한 세션에서 파이프라인으로 진행한다. 부모는 source를 직접 수정하지 않고 Planner·Publisher·Generator·Refactorer·Watcher를 하위 에이전트로 호출한다. 작은 수정이라도 호출을 생략하지 않는다. 이 문서의 계약은 `orchest` 세션에만 적용하며 `logic`·`ui`·`review`·`generate` 세션은 기존 방식을 그대로 쓴다. 부모 세션은 다음 순서로 조율한다.

1. 사용자 요청을 받고 현황판과 실제 worktree 목록을 조회한다.
2. **계획 조사(Planner 1차)**: 계획을 세우는 데 필요한 만큼만 조사한다. 작업 범위, 영향받는 계약, 재사용 후보가 있는지, 진행 중인 작업과 겹치는지를 확인한다. 겹치면 그 범위의 조사를 미루고 대기 또는 분기 방안을 정리한다. 구현에 쓸 상세 코드 탐색은 여기서 하지 않는다.
3. 범위를 확정하고 `plan.md`를 작성한다. 작업 branch·worktree, 직접 부모와 병합 순서, 겹치는 범위의 처리 방법, 작업 항목별 담당을 포함한다.
4. 현황판에 `생성 승인 대기`로 등록하고, 계획과 생성할 Git 작업을 사용자에게 승인받는다.
5. 승인 후 branch·worktree를 만들고 직접 부모 관계를 등록한 뒤 `작업 중`으로 기록한다.
6. **상세 탐색(Planner 2차)**: Planner를 작업 worktree에서 다시 호출한다. Planner는 `cd <worktree>`로 작업 위치를 옮긴 뒤 관련 스킬과 그 worktree의 대상 코드·재사용 자산을 읽고, 탐색을 마친 뒤 `exploration.md`를 한 번에 작성한다. 계획과 다른 사실과 미확정 질문은 모아서 한 번에 반환한다. 부모는 사용자 결정을 한 번에 받은 뒤 계획을 한 번만 고쳐 다시 승인받는다. 다르지 않으면 그대로 진행한다.
7. 구현 하위 에이전트가 같은 worktree에서 구현하고 포맷·검증한다.
8. Watcher가 검토하고 판정을 기록한다(`리뷰 중`). 반려되면 `workflows.md`의 재시도 규칙으로 재작업한다.
9. 미커밋 상태로 사용자에게 알린다(`사용자 검토 대기`).
10. 사용자 검토 후 승인된 commit을 실행하고 `커밋됨`으로 기록한다.
11. 직접 부모로 병합하고(`병합됨`) branch·worktree를 정리한다(`제거됨`).

### 근거는 작업 worktree 안에서 읽는다

source 수정을 허용하는 스킬·탐색 근거는 worktree마다 따로 기록되고, 그 worktree의 경로·branch·HEAD가 같을 때만 유효하다. 계획을 세운 위치에서 읽은 근거는 나중에 만든 작업 worktree의 근거가 되지 않는다.

- 스킬 근거는 읽는 순간의 작업 위치가 속한 worktree에 기록된다. 그래서 먼저 `cd <worktree>`를 단독 명령으로 실행해 작업 위치를 옮긴 뒤 읽는다. `cd … && cat …`처럼 한 줄로 이어 쓰면 인정되지 않는다.
- 탐색 근거는 읽은 파일이 속한 worktree에 기록된다. 작업 worktree의 파일을 읽어야 한다.
- 근거는 세션과 worktree 단위다. 6단계에서 Planner가 확인하면 같은 worktree의 구현 하위 에이전트에도 유효하다.
- 같은 worktree에서 commit 등으로 HEAD가 바뀌면 근거가 무효가 된다. 다음 하위 에이전트를 호출하기 전에 부모가 그 worktree에서 근거를 먼저 기록한다. `cd <worktree>`를 단독으로 실행하고, 작업에 해당하는 `SKILL.md` 하나와 대상 source 파일 하나의 앞부분을 각각 읽으면 된다. worktree를 만든 직후에 Planner 2차 없이 구현 하위 에이전트를 바로 호출하는 경우에도 같다.
- 작업 공간을 나누지 않고 계획을 세운 worktree에서 그대로 구현하는 작업은 2단계와 6단계를 한 번에 할 수 있다.
- 여러 작업을 함께 진행하면 하위 에이전트마다 자기 작업 worktree로 위치를 옮긴 뒤 읽는다.

### 부모의 책임

- 하위 에이전트를 호출할 때 작업 worktree 절대 경로, 작업 범위, 사용자가 확정한 결정, 읽을 정책과 산출물 위치를 지시에 포함한다.
- 하위 에이전트가 반환한 미확정 질문을 모아 사용자에게 묻고, 받은 답변을 해당 작업자에게 전달한다. 답변이 없는 항목은 미확정으로 두고 그 결정에 의존하는 작업을 보류한다.
- Git 변경은 하위 에이전트의 요청을 검토해 대상·명령·영향을 사용자에게 제시하고 승인 후 보호 실행기로 실행한다.
- 단계가 바뀔 때 현황판을 갱신한다. 하위 에이전트는 현황판을 조회만 한다.
- 계획이 작업 항목에 지정한 하위 에이전트를 그대로 호출한다. UI·스타일은 Publisher, 로직은 Generator, 로직의 구조 정리는 Refactorer다. 배정을 바꾸려면 계획을 고쳐 다시 승인받는다.
- 같은 worktree의 포맷·검증·Git 변경은 순차로 실행한다. 구현도 순차가 기본이며, 연결 계약이 확정되고 수정 파일이 겹치지 않는 Publisher와 Generator만 병렬로 호출한다. 병렬 구간에서는 두 에이전트에 포맷·검증을 실행하지 말라고 알리고, 둘 다 끝난 뒤 부모가 실행한 다음 최종 연결을 Generator에 맡긴다.

### 하위 에이전트 호출 비용

하위 에이전트는 호출될 때마다 정책과 문서를 처음부터 읽는다. 차단되거나 중단된 호출과 큰 컨텍스트를 다시 여는 호출은 그 비용을 그대로 버린다. 부모는 다음을 지킨다.

- **근거를 먼저 기록한다.** worktree를 만들었거나 그 worktree에 commit한 직후에는 위 절의 방법대로 부모가 그 worktree에서 근거를 먼저 기록한 뒤 하위 에이전트를 호출한다. 하위 에이전트의 첫 수정이 근거 부족으로 막히지 않게 하기 위해서다.
- **삭제는 Git 작업으로 처리한다.** 셸 `rm`은 모든 호출에서 막히고 하위 에이전트는 Git 변경을 실행하지 못한다. 추적 중인 파일의 삭제는 계획에 부모의 Git 작업으로 적어 승인 요청에 포함한다. 담당 구현 에이전트가 참조를 정리하고 삭제 요청을 반환하면 부모가 보호 실행기로 `git rm -- <경로>`를 실행하고, 포맷·검증과 Watcher 검토는 그 뒤에 한다. 아직 추적되지 않은 파일은 사용자에게 삭제를 요청한다.
- **지시는 문서의 위치를 가리킨다.** `plan.md`·`exploration.md`의 내용을 지시문에 다시 풀어 쓰지 않고 경로와 절 번호로 가리킨다. 지시문에는 작업 ID, worktree 절대 경로, 산출물 위치, 맡길 절, 문서에 아직 없는 확정 결정과 병렬 구간 여부만 적는다.
- **작은 후속 작업은 새 하위 에이전트에 맡긴다.** 테스트 실패 수정이나 Watcher의 수정 요구처럼 입력이 작은 후속 작업은 큰 컨텍스트를 가진 이전 하위 에이전트를 재개하지 않고, 실패 목록·대상 경로·관련 문서의 절만 담아 새 하위 에이전트를 호출한다. 재개는 이전 맥락 없이는 이어갈 수 없는 작업에만 쓴다.
- **검증 결과를 Watcher에 전달한다.** 부모가 포맷 뒤에 lint·test·build를 실행했으면 실행한 명령, 검증 결과와 그때의 지문을 Watcher에 전달한다. Watcher는 그 지문이 검토 시작 지문과 같으면 같은 전체 검증을 반복하지 않고 변경 파일 검토와 필요한 부분의 재실행에 집중한다.
- **사용 한도가 임박하면 호출을 미룬다.** host가 사용 한도 임박을 알렸거나 직전 하위 에이전트가 한도로 중단됐으면 새 하위 에이전트를 호출하지 않는다. 현황판과 문서에 현재 단계를 남기고 사용자에게 알린 뒤 한도가 풀리면 이어간다.
- **부모의 컨텍스트를 작게 유지한다.** 하위 에이전트의 보고는 결과·변경 경로·검증·미확정 질문·Git 요청만 받는다. 큰 명령 출력은 대화에 싣지 않고 파일로 남겨 필요한 부분만 읽는다.

## 하위 에이전트 공통 계약

`orchest` 세션의 하위 에이전트 정의에는 역할 본문과 공통 계약, 세션 바인딩이 직접 들어간다. 원본은 중앙의 `policy/common/agents/`와 `policy/common/CHILD_AGENT_CORE.template.md`이며 3개 host에 같은 내용이 설치된다. 공통 계약의 요지는 다음과 같다.

- 미확정 결정은 근거·누락 항목·선택지·영향과 함께 부모에게 반환하고, 사용자에게 직접 묻거나 대신 결정하지 않는다.
- 부모가 전달한 worktree 절대 경로에서만 작업하고 첫 변경 전에 실제 위치·branch·HEAD를 확인한다.
- Git 변경과 현황판 갱신은 실행하지 않고 요청으로 반환한다.
- 전달받은 범위 밖의 파일이나 공용 항목은 변경 전에 반환한다.
- 선행 작업의 변경 파일 목록을 받으면 그 파일만 다시 조사한다.

| 역할 | 우선 조사 | 필수 반환 |
| --- | --- | --- |
| Planner | 요구사항, 현재 구조, 재사용 자산, 영향받는 계약, 현황판과 worktree | 계획, 미확정 질문, 작업 분담, 검증, 승인받을 Git 작업 |
| Publisher | `DESIGN.md`, 공용 UI, CSS·전역 스타일·토큰·테마 | UI 계약, 재사용 결과, 구현 내용, 연결 조건 |
| Generator | 기존 API·DTO·hook·상태·유사 구현과 관련 정책 | 변경 내용, 검증, 미확정 사항, 리뷰 요청 |
| Refactorer | 기존 동작, 호출자·의존성·공개 계약·테스트 | 보존한 동작, 구조 변경, 검증, 리뷰 요청 |
| Watcher | 승인된 요구·계획, 관련 정책, 검토 대상 버전과 검증 근거 | 위치·근거·영향이 있는 발견 사항과 수정 요구 |

### 역할별 작업 방식

`orchest` 세션의 하위 에이전트는 기존 UI·Logic 세션의 작업 방식을 그대로 적용한다. 각 정의의 세션 바인딩에 적용할 역할 계약 문서와 주로 쓰는 스킬 경로가 들어간다.

| 하위 에이전트 | 적용하는 역할 방식 | 예 |
| --- | --- | --- |
| Planner | 오케스트레이션·기획 | 현황판 조회, 범위·병합 순서 계획 |
| Publisher | UI | `DESIGN.md`·공용 UI 조사, `ui-asset-plan.md`, 스타일·접근성 기준. 화면 구조·스타일 리팩터링 포함 |
| Generator | Logic | `api-authoring` 패턴대로 API 연결, 공통 응답 DTO 재사용, controller 계약 |
| Refactorer | Logic | 동작·공개 계약 보존, `refactoring` 기준 |
| Watcher·Evaluator | 리뷰 | `review-checklist`, 검증 근거 |

### 단계별 문서와 판정 기록

오케스트레이션 세션은 단계마다 문서를 남기고, 다음 단계는 그 문서가 있어야 시작된다. 위치는 세션 산출물 폴더이며 현황판에 계획을 등록한 작업은 `tasks/<작업 ID>/`다.

| 단계 | 작성자 | 문서 | 확인 시점 |
| --- | --- | --- | --- |
| 계획 | Planner | `plan.md`, `exploration.md` | source 수정 전 |
| 구현 | Publisher·Generator·Refactorer | `implementation-log.md` | Watcher 판정 기록 전 |
| 검토 | Watcher | `review-log.md`, `verdict` 기록 | 판정 기록 전, 커밋 준비 전 |
| 완료 | 부모 | `final-summary.md` | 병합 준비 전 |

- 내용이 없는 문서는 작성한 것으로 보지 않는다.
- Watcher는 검토 시작 지문을 `verdict --start`에 넘긴다. 검토 중 대상이 바뀌면 기록이 거부된다.
- 커밋 준비와 실행 직전에 PASS 기록의 지문과 현재 지문을 대조한다. 지문은 HEAD와 변경·신규 파일의 내용으로 계산하며 stage 여부와 세션 문서는 영향을 주지 않는다. 검토 뒤의 포맷·수정은 다시 검토받아야 하므로 포맷과 검증을 먼저 끝내고 Watcher를 호출한다.
- 변경된 source가 없고 세션 문서만 커밋하는 경우에는 판정을 요구하지 않는다.

### 작업 항목 배정 기준

Planner는 계획의 작업 항목마다 변경 종류와 담당 하위 에이전트를 지정하고, 부모는 그 배정대로 호출한다. 생성·수정·삭제에 같은 기준을 적용한다.

| 담당 | 변경 대상 |
| --- | --- |
| Publisher | 마크업, 컴포넌트 구조, CSS·스타일·디자인 토큰, 정적 자산, 접근성, 반응형 표현의 생성·수정·삭제와 이들의 리팩터링 |
| Generator | API, DTO, parser, validator, hook, util, store, 상태 전이, controller의 생성·수정·삭제 |
| Refactorer | 위 로직 영역에서 동작을 바꾸지 않는 구조 정리 |

- 삭제 항목은 담당 구현 에이전트가 참조 정리를 맡고, 추적 중인 파일을 지우는 실행은 부모의 Git 작업(`git rm`)으로 계획한다. 하위 에이전트는 셸 `rm`과 Git 변경을 실행하지 못한다.
- 한 파일에 UI와 Logic 변경이 섞이면 Publisher가 UI 계약(props·callback)을 먼저 확정하고 Generator가 연결하는 순서로 나누어 순차 진행한다.
- 하위 에이전트는 자기 배정 밖의 변경이 필요해지면 직접 하지 않고 부모에게 반환한다. 배정을 바꾸려면 계획을 고쳐 다시 승인받는다.
- 하위 에이전트 호출을 식별하는 host에서는 부모와 Planner·Watcher의 source 쓰기를 guard가 거부한다. Publisher와 Generator·Refactorer 사이의 변경 종류 구분은 프롬프트 계약이며 훅이 막지 않는다.

### UI와 Logic의 병렬 구현과 최종 연결

화면 요구가 있는 작업은 연결 계약을 먼저 확정한 뒤 UI와 Logic을 병렬로 구현하고, 둘 다 끝나면 연결한다.

1. **계약 확정**: Publisher가 디자인(Figma가 연결된 host에서는 Figma)과 요구에서 화면이 필요로 하는 데이터·상태·입력·동작을 UI 계약 초안으로 정리한다. Planner는 이를 실제 API·DTO 근거와 대조해 controller 공개 타입(데이터, 상태, callback)을 `plan.md`의 UI·Logic 연결 계약에 기록한다. 맞지 않거나 확인되지 않은 항목은 사용자에게 질문하고, 계약은 계획과 함께 승인받는다.
2. **병렬 구현**: Publisher는 계약의 props·callback으로 화면을 구현하고, Generator는 API부터 UI 없는 controller까지 구현한다. 두 에이전트의 수정 파일은 겹치지 않아야 한다. 겹치면 순차로 진행하거나 작업 공간을 나눈다.
3. **계약 변경**: 병렬 구간에서 계약과 다른 사실이 발견되면 해당 에이전트가 그 부분을 보류하고 반환한다. 부모가 사용자 결정을 받아 계약을 갱신하고 양쪽에 전달한다.
4. **최종 연결**: 둘 다 끝나면 부모가 포맷과 검증을 실행한 뒤 Generator가 page·container에서 controller를 View에 연결한다. 연결 뒤 다시 포맷·검증하고 Watcher가 검토한다.

같은 worktree의 병렬 구간에서는 하위 에이전트가 포맷과 lint·test·build를 실행하지 않는다. 포맷과 검증 전 자동 포맷이 상대가 편집 중인 파일까지 다시 쓰기 때문이다. 부모가 두 에이전트의 종료를 확인한 뒤 실행한다.

`logic`·`ui`·`review`·`generate` 세션은 이 계약의 대상이 아니며 기존 정의와 방식을 그대로 쓴다. Figma MCP는 Claude Code의 `ui`·`orchest` 세션에 제공되며 `orchest` 세션에서는 Publisher가 사용한다.

## 작업 현황판

현황판은 브랜치 관계 그래프 옆에 작업별 단계·범위·대기를 기록한다. 명령은 system prompt에 바인딩된 보호 실행기 경로를 사용한다.

| 명령 | 용도 |
| --- | --- |
| `board` | 브랜치·워크트리 관계, 병합 순서, 작업 단계와 실제 Git 상태를 조회한다 |
| `board --check <경로>` | 공용 항목을 바꿀 때 범위가 겹치는 작업과 다른 worktree의 참조 후보를 확인한다 |
| `board-set --task <ID> ...` | 단계·branch·범위·공용 항목·`plan.md` 위치·대기를 기록한다 |
| `board-wait --task <ID>` | 선행 작업이 커밋될 때까지 기다린 뒤 변경된 파일을 출력한다 |
| `fingerprint` | 현재 worktree의 검토 지문을 출력한다 |
| `verdict --result PASS\|FAIL --start <지문>` | Watcher의 판정을 현재 지문과 함께 기록한다. 커밋 준비 때 확인한다 |

- 단계는 `planning`(계획 중), `awaiting-creation`(생성 승인 대기), `working`(작업 중), `reviewing`(리뷰 중), `awaiting-user-review`(사용자 검토 대기), `committed`(커밋됨), `merged`(병합됨), `removed`(제거됨), `cancelled`(취소)다.
- `working` 이후 단계는 실제 branch가 있어야 하고, `committed`는 미커밋 변경이 없을 때, `merged`는 등록된 직접 부모에 포함됐을 때, `removed`는 branch가 없을 때만 기록된다.
- 기록은 소유권·허용 파일 목록·쓰기 잠금을 만들지 않는다. 범위가 겹쳐도 등록을 막지 않고 겹치는 작업을 알려 준다. 겹치면 선행 작업을 기다리거나 분기해 접점 밖을 먼저 작업하는 안을 계획에 넣고 사용자 승인을 받는다.
- 병합 순서는 브랜치 관계가 강제한다. 분기한 작업은 자식에서 직접 부모로 먼저 병합한다.
- 구현이 끝났지만 병합 전인 작업은 기록을 유지한다. 다른 세션이 이전 기준 branch에서 같은 범위를 시작하지 않게 하기 위해서다.
- 세션이 종료·중단되어 기록만 남은 작업은 `board`의 실제 Git 상태(`actual`)와 worktree·diff·미확인 쓰기 기록을 확인하고 사용자에게 확인받은 뒤 해당 단계부터 이어간다. 시간 경과나 기록만으로 완료 처리하지 않는다.

### 공용 항목 변경

Planner는 shared·lib·utils·공용 UI·hook의 생성·수정·삭제가 필요하다고 판단하면 `board --check`를 실행한다. 결과의 `tasks`는 범위가 겹치는 진행 중 작업, `usage`는 다른 worktree에서 그 경로를 참조하는 파일 후보다. 후보는 문자열 일치이므로 실제 import·타입·props 영향은 직접 확인한다. 영향받는 위치와 다음 선택을 계획에 넣어 사용자에게 질문한다.

- 별도 branch·worktree의 독립 작업으로 둘지, 현재 작업 branch 안에서 선행 작업으로 처리할지
- 그에 따라 바뀌는 병합 순서와 영향받는 작업의 재조사 범위

### 대기와 재계획

1. 범위가 겹치는 선행 작업이 있으면 `board-set --wait-for <선행 ID>`로 대기를 기록한다. 접점 경로와 그 시점의 선행 HEAD가 함께 기록된다.
2. 선행 작업이 `committed`가 되면 대기가 풀린다. `board-wait`의 출력, SessionStart 안내 또는 다음 사용자 입력의 안내에 접점 경로에서 변경된 파일이 나온다.
3. 그 파일만 다시 조사해 계획을 갱신한다. 이미 조사한 내용은 다시 조사하지 않는다. 필요한 사용자 결정이 달라진 경우에만 다시 질문한다.
4. 재계획을 마치면 `board-set --clear-wait`로 대기를 해제하고, 구현은 갱신한 계획의 승인 후 진행한다.

host가 백그라운드 명령의 종료를 세션에 알려 주면 `board-wait`를 백그라운드로 실행해 재계획까지 자동으로 이어갈 수 있다. 그렇지 않은 host에서는 다음 사용자 입력 때 안내를 받는다. 작업들이 서로를 기다리게 되는 등록은 거부되며, 의존 관계와 대기 이유를 사용자에게 보고한다. 우선순위를 임의로 바꾸거나 다른 작업의 대기를 강제로 풀지 않는다.

## 토큰 사용량 분석

사용자가 `토큰 분석`을 입력하면 그 세션에서 병합한 작업마다 정리 전에 토큰 사용량 보고서를 쓴다. 절차와 보고서 구조는 `policy/token-usage/SKILL.md`에 있다.

- 요청은 세션이 끝날 때까지 유지되고 `토큰 분석 취소`로 거둔다.
- 요청이 있으면 병합과 정리를 나눈다. `review`는 `--cleanup` 없이 준비해 병합만 완료하고, 보고서(`unknown/token-usage-report.md`)를 쓴 뒤 `cleanup --source <branch> --target <직접 부모>`로 정리한다.
- guard는 정리를 함께 하는 완료를 막고, 보고서가 없거나 직접 부모의 마지막 commit보다 먼저 쓰였으면 정리를 막는다.
- 보고서는 부모가 쓴다. 분석을 하위 에이전트에 맡기지 않는다.

## 현재 실행 하네스의 경계

역할별 산출물·Watcher 평가 지침과 agent별 실행 격리는 구분한다. 준비 근거는 assignment 안의 worktree별이고, 계획 binding과 포맷 작성자는 세션 단위다. 부모의 역할 환경을 자식 역할 승인으로 해석하지 않는다.

하위 에이전트 호출을 부모와 구분할 수 있는지는 host마다 다르다.

| host | 도구 실행 전 이벤트의 식별 | 하위 에이전트의 Git 변경 |
| --- | --- | --- |
| Claude Code | `agent_id` 제공 | 공통 guard가 거부 |
| Codex | 제공하지 않음(부모 `session_id` 사용) | 프롬프트 계약으로만 운영 |
| OpenCode | 확인되지 않음 | 프롬프트 계약으로만 운영 |

Claude Code에서는 하위 에이전트가 끝날 때 그 대화 기록에 없는 호출이 남긴 쓰기 예약을 자동으로 해소한다. 병렬 호출이 취소되면 실행 전 검사만 남고 결과가 기록되지 않아 같은 worktree의 commit을 막기 때문이다. 결과까지 기록됐지만 실행 후 검사가 끝나지 않은 호출의 예약도 해소한다. 이때 바뀐 파일은 결과 미확인으로 남으므로, 내용을 확인한 뒤 수정 도구로 다시 저장해야 포맷된다. 결과가 기록되지 않은 호출은 남기며, 이때는 `writes`로 확인하고 실제 종료를 확인한 뒤 `write-recovery`로 해소한다.

식별이 확인되지 않은 host에 대해 하위 에이전트의 Git 변경이나 부모의 source 쓰기가 차단된다고 보고하지 않는다. 식별하는 host에서는 `orchest` 세션의 부모와 Planner·Watcher의 source 쓰기를 guard가 거부한다. 사용자가 `직접 수정 승인`을 입력하면 그 응답 동안만 부모가 직접 수정할 수 있고 다음 사용자 입력에서 다시 막힌다. 단계별 문서와 커밋 전 Watcher PASS 확인은 모든 host에 적용된다. 다만 식별하지 못하는 host에서는 판정을 누가 기록했는지 확인하지 못한다.

## 한 세션의 여러 작업

API 명세처럼 하나의 요청에서 여러 작업이 나오면 부모 세션이 작업마다 branch·worktree를 만들고 하위 에이전트를 배치할 수 있다.

- 구조는 평면이다. 하위 에이전트는 다른 하위 에이전트를 호출하지 않는다. 부모가 작업마다 Planner·Publisher·Generator·Refactorer·Watcher를 직접 호출하고 Generator ↔ Watcher의 왕복도 부모가 중계한다.
- 작업마다 산출물 폴더 `tasks/<작업 ID>/`를 세션 산출물 아래에 두고 `plan.md`, `implementation-log.md`, `review-log.md` 등을 작성한다. 세션 최상위의 `plan.md`와 `final-summary.md`는 전체 작업 목록·의존 관계·병합 순서와 결과를 요약한다.
- 작업의 계획은 `board-set --task <ID> --plan <tasks/<ID>/plan.md의 경로>`로 등록한다. 등록된 worktree의 source 변경은 그 작업 계획의 승인으로 판정한다.
- 사용자는 `<작업 ID> 진행`으로 작업별 계획을 승인한다. 여러 작업을 한 번에 승인하려면 `<ID> <ID> 진행`처럼 ID를 나열한다. 작업 ID가 없는 `진행`은 작업 계획을 승인하지 않는다. 취소는 `<작업 ID> 구현 승인 취소`다. 부모는 승인을 요청할 때 작업 ID와 각 계획을 구분해 제시한다.
- 하위 에이전트를 호출할 때 작업 ID, worktree 절대 경로, 작업 범위, 확정된 결정과 `tasks/<작업 ID>/` 산출물 위치를 전달한다. 한 하위 에이전트에 여러 작업의 worktree를 맡기지 않는다.
- Git 변경, 현황판 갱신, 사용자 질문·승인은 부모가 작업 ID를 붙여 처리한다. 같은 worktree의 포맷·검증·Git 변경은 순차로 실행하고, 서로 다른 worktree의 작업은 병렬로 진행할 수 있다.
- 작업 사이에 범위가 겹치면 대기와 재계획 절차를 그대로 적용한다.

### 중단 후 재개

- 원래 세션을 `resume`으로 재개하면 assignment가 같으므로 작업별 승인과 준비 근거가 유지된다. 현황판과 실제 Git 상태를 대조한 뒤 이어간다.
- 새 세션에서 이어가면 `board`의 `resumable`에 다른 세션이 기록한 미완료 작업과 실제 Git 상태가 나온다. 작업의 `plan.md`, worktree·diff와 미확인 쓰기 기록을 확인하고 사용자에게 확인받은 뒤 해당 단계부터 진행한다. 계획 승인은 승계되지 않으므로 `<작업 ID> 진행`으로 다시 받는다. `board-set`으로 단계를 갱신하면 담당 세션 표시가 현재 세션으로 바뀐다.
- 다른 host의 세션이 작성한 산출물은 읽기 전용이다. 이어가는 세션은 자기 세션의 `tasks/<작업 ID>/`에 기록을 이어 쓰고 이전 기록의 위치를 연결한다.
