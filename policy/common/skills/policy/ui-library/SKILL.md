# UI 자산 선정과 라이브러리

## 계획 단계의 필수 문서

UI 구현을 계획하는 모든 작업에서 규모, host, 역할과 `owner`·`contributor` 구분에 관계없이 현재 세션의 `unknown/ui-asset-plan.md`를 생성한다. 신규 화면, 기존 화면 수정과 UI 리팩터링을 포함한다. 외부 라이브러리를 쓰지 않아도 작성한다. `plan.md` 또는 `handoff.md`에서 연결하고, 구현 항목이나 선택이 바뀌면 같은 문서를 갱신한다. UI 구현 계획이 없는 조사·리뷰와 기존 변경의 commit·merge만 수행하는 요청에는 새 문서를 요구하지 않는다.

계획·구현 승인 요청 전에 [자산 선정 템플릿](references/ui-asset-plan.template.md)으로 문서를 작성해 사용자에게 제시한다. 이 계획 산출물의 작성은 승인 전 애플리케이션 소스·패키지·정책 변경 허가가 아니다. 인계받은 문서는 읽기 전용 근거로 참조하고 현재 코드·요구와 대조한 판단을 자기 세션에 기록한다.

먼저 현재 프로젝트의 `package.json`, lockfile, 설정, `src/shared/ui/`와 실제 공용 경로, 인접 UI 및 다른 도메인의 구현·사용처를 조사한다. 카탈로그나 이름만으로 자산의 존재·적합성을 단정하지 않는다. 여기서 다른 도메인은 같은 소비자 프로젝트 안의 기능 영역이며 세션의 프로젝트 실행 경계를 확장하지 않는다.

각 UI 구현 항목에 다음 선택을 대응시킨다. 한 항목에 여러 자산이 필요하면 자산별로 행을 나눈다.

| 선택 | 판단과 기록 |
| --- | --- |
| 기존 공용 자산 재사용 | 실제 경로·사용처, 공개 계약, 요구 충족 범위와 필요한 확장 |
| 다른 도메인 자산 공용화 | 원본·기존 소비자, 승격 위치, 도메인 의존 제거와 기존 호출 계약 보존·이전 방법 |
| 외부 라이브러리 사용 | 패키지·설치 버전, 선택 목적, 기존 자산으로 충족하지 못하는 요구, 어댑터 경로·계약과 라이브러리 스킬 경로 |
| 요구사항의 구현 항목을 공용 자산으로 신규 작성 | 요구사항 항목, 명시된 공용 목적, 재사용 대상·범위, 구현 위치와 최소 공개 계약 |

모든 항목에 선택·제외 이유, 조사 근거, 적용할 props·이벤트·상태 계약, 예상 변경·검증과 결정 상태를 기록한다. UI 항목을 누락하거나 자산 목록만 나열하지 않는다. 적합한 자산이나 계약이 확인되지 않으면 미정으로 기록하고 기존 재사용 확인 규칙에 따라 질문한다. 네 선택으로 충족할 수 없어 도메인 로컬 구현이 필요하면 근거와 대안을 제시하고 사용자에게 확인받는다.

현재 코드·컴파일러·상태 관리 방식에 근거해 번들·추가 의존성, 렌더링·구독 범위와 기존 사용처에 미치는 영향을 기록한다. 측정값과 예상 영향을 구분하며 근거 없는 메모이제이션이나 범용 옵션을 추가하지 않는다. 공용 신규 작성은 요구사항에 명시된 재사용 목적과 계약으로 정당화할 수 있으며, 미래 가능성만으로 추상화하지 않는다.

## 외부 UI 라이브러리와 스킬

외부 기본 요소는 반드시 `src/shared/ui/`의 공용 어댑터에서 감싸고 기능 코드는 공급자 패키지 대신 어댑터에서 가져온다. 새로운 UI 의존성을 도입하기 전에 사용자에게 확인받는다. 이미 승인한 동일 의존성·재사용 결정은 다시 묻지 않는다.

작업 범위에서 직접 또는 공용 어댑터를 통해 사용하는 외부 UI 라이브러리는 신규 도입·기설치 여부와 관계없이 라이브러리별 `SKILL.md`를 갖춘다. 먼저 주입된 `reference/libraries/`와 기존 관련 스킬을 조사한다. 대상 프로젝트·버전·계약에 맞는 문서가 있으면 검증해 연결하고, 내용이 달라지면 갱신하며, 없으면 새로 작성한다. 설치된 모든 패키지를 일괄 문서화하지 않는다.

[라이브러리 스킬 템플릿](references/external-ui-library-skill.template.md)을 사용해 다음을 문서화한다.

- 사용 목적, 해결할 요구, 적용·제외 범위, 선택 근거와 대상 프로젝트
- 정확한 패키지명, 선언·설치 버전과 확인한 공식 문서·실제 코드 경로
- 공용 어댑터 위치·의존 방향·공개 import와 공급자 API를 감추는 구현 방식
- props·타입·기본값, controlled 상태·변경 callback·이벤트 payload, ref·children 및 접근성·스타일 계약 중 해당 항목
- 필요한 provider·CSS·설정과 실제 어댑터를 사용하는 최소 예시, 제약·주의사항 및 검증 방법

계획 단계에서 목적·선택과 제안 계약을 작성하고 실제 사용 전에 스킬 초안을 갖춘다. 구현 후 실제 경로·계약·사용 예시·검증 결과와 일치하도록 갱신한다. 계획·제안과 확인된 구현을 구분하며 존재하지 않는 API나 사용처를 사실로 기록하지 않는다.

## 중앙 등록과 인계

소비자 세션은 `unknown/ui-library-skills/<library>/SKILL.md`에 신규 문서 또는 갱신 초안을 작성한다. `<library>`는 소문자·숫자·하이픈으로 만든 식별자이며 원래 패키지명은 문서에 별도 기록한다. 소비자의 관리 스킬 경로나 정책 파일을 직접 생성·수정하지 않는다.

중앙 등록·갱신은 중앙 저장소 작업으로 인계한다. 새 정본의 기본 위치는 중앙의 `policy/common/skills/reference/libraries/<library>/SKILL.md`이며 기존 정본이 있으면 그 위치를 우선한다. handoff에는 초안·기존 정본·대상 중앙 경로, 이유·예상 diff, 대상 프로젝트·버전, 검증과 미완료 사항을 남긴다. 임의 프로젝트 overlay를 만들지 않는다.

중앙 문서에는 실제 확인한 프로젝트별 적용 조건을 명시하고 모든 소비자에 해당 패키지나 어댑터가 있다고 가정하지 않는다. 중앙 검증 후 새 inject 세션에서 등록 문서를 사용한다. 등록 전에는 세션 초안임을 표시하고 중앙 스킬 등록까지 완료했다고 보고하지 않는다.
