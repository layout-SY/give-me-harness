# 계획 스키마

필수 항목: 목표, 작업 유형, 범위, 제외 사항, 제약 조건, 역할과 판단 근거, 사용자 확인, 승인할 Git 작업, 선택한 스킬, 작업 구간, 검증, 위험 요소와 승인 상태.

`plan.template.md`의 `asan-plan:approval:start:v1` / `asan-plan:approval:end:v1` 표식 사이만 구현 승인 해시의 대상이다. 각 표식은 한 줄에 한 번씩 쓰며 목표·범위(대상 worktree 포함)·역할·변경 계약·검증 및 완료 기준을 담는다. 줄바꿈과 줄 끝 공백을 정규화한 내용으로 비교한다. 영역 밖의 진행·검증 결과·장애·인계·승인 상태 갱신은 해시에 포함하지 않는다. 새 요구나 계약 변경을 진행 기록에만 남겨 이전 승인을 재사용하지 않는다.

승인 영역이 바뀌면 변경분을 보고하고 **같은 세션에서** 구현 승인을 갱신한다. 세션을 폐기하지 않는다. 표식이 없는 기존 계획은 전체 파일 해시를 유지하므로 새 형식으로 전환할 때 한 번 재승인을 받는다. 잘못된 표식·빈 승인 영역·없거나 비어 있는 계획은 소스 구현을 차단하며 자기 계획 작성·수정과 읽기 조사는 가능하다. hook은 계획 내용의 품질이나 구현과의 의미적 일치까지 증명하지 않는다.

같은 세션이 여러 worktree를 작업하면 승인 영역의 대상과 각 위치의 작업 범위를 명시한다. 하나의 승인 계획을 참조할 수 있지만, 실제 스킬·탐색 근거는 대상 worktree·branch·HEAD·역할마다 따로 확인한다. 다른 worktree에 진행 로그를 남기는 것만으로 새 구현 준비가 완료되지는 않는다. 다른 세션은 자기 계획과 준비를 작성한다.

UI 구현을 계획하면 `ui-library`에 따른 `unknown/ui-asset-plan.md`를 승인 요청 전에 생성하고 연결한다. 외부 UI 라이브러리를 사용하면 관련 사용 스킬·세션 초안과 중앙 등록·갱신 상태를 포함한다. UI 구현 계획이 없으면 해당 없음의 근거를 기록한다.

UI·API 연결은 `api-authoring/references/ui-controller.md`에 따라 선행 구현·계약 제공자·맞추는 방향, UI/controller·DTO 경로, 양방향 매핑과 불일치에 대한 사용자 질문·답변을 기록한다.
